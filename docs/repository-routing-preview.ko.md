# Laya 라우팅 적합성과 GitHub 저장소 선택 preview

## 판단: 할 수 있는 일과 아직 입증하지 못한 일

Laya는 주어진 텍스트와 유한한 선택지 사이에서 선택하는 분류기입니다. 저장소 이름·역할·짧은 설명을 후보로 주는 작업은 형식적으로 맞습니다. 그러나 **형식에 맞는 출력과 올바른 선택은 다릅니다.** 선택지 밖의 이름을 생성하지 않아도 잘못된 저장소를 고를 수 있습니다.

모델 선택과 저장소 선택도 구분해야 합니다. 저장소 선택은 “어디가 이 기능을 담당하는가”라는 설명 기반 분류입니다. 모델 선택은 “어떤 코딩 모델이 이 일을 충분히 잘 끝낼 것인가”라는 결과 예측입니다. 후자에는 작업 성공률·실패 비용·재시도·실제 사용량의 라벨이 필요합니다. 작업이 짧다는 이유만으로 쉬운 작업이라고 판정할 수 없고, Laya의 확률을 코딩 모델의 성공 확률로 해석해서도 안 됩니다.

[Laya의 현재 상위 README](https://github.com/NandhaKishorM/laya)는 영어 base, 별도 multilingual, typed-decisions 체크포인트를 구분합니다. **우리가 설치한 root base는 영어 ModernBERT 421M/512토큰**이며, 해당 프로젝트의 다국어·긴 컨텍스트 주장이 그대로 적용되지 않습니다. 별도 multilingual 모델은 토크나이저와 그래프를 다시 검증해야 하므로 파일 이름만 바꿔 끼우지 않았습니다.

[고정 base 모델 카드](https://huggingface.co/convaiinnovations/laya/blob/55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851/README.md)도 도메인별 확률 보정 필요성, 언어에 따라 높은 확신도로 틀릴 수 있는 문제, 질문/선택지 표현의 영향을 설명합니다. 일반 벤치마크의 확률 보정이 뤼이도의 모델·저장소 선택 정확도를 보장하지 않습니다. `laya-code`는 [자체 모델 카드](https://huggingface.co/tindang/laya-code/blob/25f97e5a2ec5f8cf7218a4f67504367d8832e1fe/README.md)에서 코드 재정렬용이며 choice/score를 학습하지 않았다고 명시하므로 이 preview에서는 base를 사용합니다.

## 뤼이도에 맞춘 구조

```text
뤼이도가 관리하는 접근 가능한 저장소 목록
  → 이름·요약·키워드의 로컬 인덱스
  → 키워드 후보 최대 4개
  → [선택 옵션] Laya: 후보 중 하나 또는 none/ambiguous
  → preview 결과: 후보 / 실험적 추천 / 보류
  → 실제 실행 연결은 아직 하지 않음
```

전체 소스 코드나 모든 README를 매번 모델에 넣지 않습니다. 저장소별 역할 요약과 별칭을 뤼이도에서 제공하면 됩니다. 초기에는 키워드 후보만으로 충분한지 먼저 측정하고, 애매한 요청에서 Laya가 추가로 도움이 되는지 비교하는 편이 합리적입니다.

`pkg/reporouter`는 표준 라이브러리만 사용하는 공개 Go 패키지입니다. 인덱스는 만들 때 목록을 복사하며, 매 요청 GitHub 조회·clone·임베딩 생성·파일 스캔을 하지 않습니다. 네이티브 모델 어댑터는 별도로 분리했습니다. 사람이 보는 텍스트, 에이전트용 JSON, 인덱스와 모델을 유지하는 JSONL 프로세스를 제공합니다.

저장소 목록은 **호출자가 접근 권한에 따라 먼저 필터링**해야 합니다. `disabled: true`는 후보에서 제외합니다. 라우터는 권한을 확인하거나 부여하는 장치가 아닙니다. 저장소 설명의 지시문 역시 실행하지 않습니다. 허용된 후보의 ID만 반환하지만, 악의적인 설명이 분류 결과에 영향을 줄 가능성까지 해결한 것은 아닙니다.

## 사용법

저장소 루트의 예제는 실제 뤼이도 저장소가 아닌 가상 목록입니다.

```sh
# 기본: 모델 없이 가벼운 후보 검색
riidolaya repo-preview --catalog examples/repositories/catalog.json --json 'refund invoices'

# 옵션: 기존 로컬 영어 Laya로 한 번 더 판단
riidolaya repo-preview --catalog examples/repositories/catalog.json --laya --json 'refund invoices'

# 여러 요청: 인덱스를 유지하고, 필요할 때 모델을 한 번 로딩
riidolaya repo-serve --catalog examples/repositories/catalog.json --laya
```

JSONL 입력:

```json
{"id":1,"query":"Fix login sessions"}
{"id":2,"query":"로그인 비밀번호 수정"}
```

카탈로그 형식:

```json
[
  {
    "name": "example/identity-api",
    "summary": "Authentication service: login and access tokens.",
    "keywords": ["auth", "로그인", "인증"],
    "disabled": false
  }
]
```

공개 Go API는 `reporouter.New(repos)`로 인덱스를 만들고 `idx.Preview(query, reporouter.DefaultConfig(), judge)`를 호출합니다. `judge == nil`이면 네이티브 모델이 필요 없습니다. 자체 어댑터는 `Judge.Choose` 인터페이스를 구현할 수 있습니다.

반환 상태는 다음 의미입니다. **모든 결과는 `preview: true`이며 실행 허가가 아닙니다.**

- `candidate`: 키워드 후보. 정확도를 보정한 자동 선택이 아님. 모델 미사용·언어 미검증·추론 실패 시에도 이 상태를 명확히 표시합니다.
- `suggest`: Laya의 실험적 선택이 확신도 0.9와 1·2위 확률 차이 0.15를 통과함. 그래도 preview입니다.
- `abstain`: 후보 없음, none/ambiguous 선택, 낮은 확신도, 입력 잘림 또는 잘못된 추론 결과. `suggested`가 비어 있습니다.

후보 수는 CLI 기본 4개, 공개 API에서 최대 8개입니다. 모델의 none 선택지를 포함해 기존 2~10 선택지 한도 안에 둡니다. 설명이 선택지 토큰 예산을 넘으면 잘림을 표시하고 추천을 보류합니다. 이를 위해 기존 토크나이저의 **선택지 잘림이 표시되지 않던 문제도 수정**했습니다. 토큰 ID를 만드는 규칙은 그대로입니다.

영어용 모델이므로 비라틴 문자가 포함된 질문/선택지 설명은 Laya를 호출하지 않고 키워드 후보만 반환합니다. 한국어 별칭은 키워드 검색에 사용할 수 있습니다. 이 규칙은 완전한 언어 감지기가 아니며 라틴 문자로 쓰인 다른 언어의 지원을 보장하지 않습니다. 모델은 영어 입력을 전제로 평가해야 합니다.

CLI 카탈로그 JSON은 1MiB, 공개 API는 메타데이터 총 4MiB/4,096개 저장소까지 받습니다. 저장소별 설명 2,048바이트, 키워드 32개, 키워드당 128바이트, 질의 8KiB 한도가 있습니다. 512토큰 모델 입력 한도는 별도이므로 큰 설명을 허용한다고 모델이 전부 읽는 것은 아닙니다.

## 첫 실측: Laya 추가의 이득을 확인하지 못함

Apple M4 Pro/24GiB, Go 1.27, CPU 4스레드, INT8 base, 2026-09-30. 가상 저장소 6개, 직접 작성한 질문 24개: 정답 저장소가 있는 영어 12개·한국어 6개, 범위 밖 4개·다중 저장소 2개입니다. 설명과 어휘가 겹치는 쉬운 개발 예제이며 독립 평가셋이나 운영 데이터가 아닙니다.

| 항목 | 키워드만 | Laya 옵션 |
|---|---:|---:|
| 정답 있는 질문의 키워드 Top-1 | 18/18 | 동일 후보 단계 18/18 |
| 정답 저장소의 후보 포함 | 18/18 | 18/18 |
| 실제 Laya 판단 | 0 | 15회(한국어·후보 없음 제외) |
| 임계값 적용 전 Laya 원시 선택 정답 | 해당 없음 | 8/15 |
| 임계값을 통과한 Laya 추천 | 해당 없음 | 0/24 |
| 정답 없는 6건에서 남은 후보/추천 | 3/6 | 0/6 |
| 요청 중앙값, 모델 로딩 제외 | 0.001ms | 39.669ms |
| 요청 p95, 모델 로딩 제외 | 0.002ms | 54.040ms |
| 모델 로딩 | 없음 | 941.815ms |
| 전체 프로세스 최대 RSS | 약 11.5MiB | 약 1,436MiB(1.40GiB) |
| Go heap, 평가 종료 시점 | 약 0.54MiB | 약 12.7MiB |

24건 전체의 시간에는 모델을 부르지 않은 요청도 포함됩니다. 첫 추론은 포함하며 모델 생성 시간만 분리했습니다. RSS는 각각 별도 프로세스의 `/usr/bin/time -l`로 측정했습니다. `go_heap_bytes`는 GC 시점에 따라 달라지고 네이티브 메모리를 제외합니다. GPU 실행이나 GPU 메모리는 측정하지 않았습니다.

0건 추천에서 정확도가 높다고 해석하면 안 됩니다. **추천 coverage가 0이므로 accepted precision은 정의되지 않습니다.** 범위 밖 후보를 없앴지만 정답 있는 영어 작업도 모두 보류해 실용적인 자동 라우팅 이점을 입증하지 못했습니다. 이를 개선했다고 보이게 하려고 임계값을 낮추지 않았습니다.

반면 키워드 단계도 무관한 '카메라 발명의 역사'나 여러 저장소를 바꾸는 요청에서 후보를 내놓았습니다. 따라서 Top-1 18/18이라는 쉬운 예제 결과만으로 자동 실행에 연결하면 안 됩니다.

규모별 순수 Go 후보 검색 마이크로벤치마크(가상 설명, 인덱스 생성/모델 추론 제외):

| 저장소 수 | 시간/요청 | 할당량/요청 |
|---:|---:|---:|
| 10 | 1.114µs | 768B |
| 100 | 12.772µs | 2,400B |
| 1,000 | 170.631µs | 16,992B |

이 할당량은 인덱스 상주 메모리가 아닙니다. 큰 카탈로그의 실제 메모리 한계는 저장소 수뿐 아니라 설명 길이와 고유 단어 수에 따라 달라집니다. 자동으로 배경 daemon을 설치하지 않았고, 키워드 모드는 모델을 로딩하지 않습니다. `repo-serve --laya`는 첫 지원 언어 요청에서 로딩 후 프로세스가 끝날 때까지 모델을 유지합니다. 기존 warm 검색 프로세스와 모델을 공유하지 않으므로 별도로 띄우면 네이티브 모델 메모리가 중복될 수 있습니다.

원본 결과: [키워드](../benchmarks/results/repo-preview-lexical.json), [Laya](../benchmarks/results/repo-preview-laya.json). 공개 예제만 사용하는 재현 명령:

```sh
go build -o bin/repoeval ./cmd/repoeval
/usr/bin/time -l ./bin/repoeval
/usr/bin/time -l ./bin/repoeval --laya
go test ./pkg/reporouter -run '^$' -bench . -benchmem
```

## 다음 검증의 우선순위

1. 뤼이도가 이미 가진 저장소 이름·역할·기능 별칭을 로컬 카탈로그로 연결합니다. 기존 선택과 preview 결과를 나란히 기록하되, 비공개 입력은 공개 저장소에 올리지 않습니다.
2. 정답 저장소 라벨을 만들고 영어/한국어, 비슷한 이름, 역할이 겹치는 저장소, 새 저장소, 정답 없음, 다중 저장소 요청을 나눕니다. 후보 recall과 최종 선택 정확도를 분리합니다. 후보에서 빠진 정답을 Laya가 되살릴 수는 없습니다.
3. 키워드만, Laya 추가, 선택적으로 다른 소형 분류기/임베딩을 같은 질문으로 비교합니다. p50/p95·cold start·RSS·추천 coverage·잘못된 추천율을 함께 봅니다.
4. 이득이 확인될 때 도메인별 학습/확률 보정 또는 별도 multilingual ONNX 이식을 검토합니다. 학습·확률 보정·최종 평가 데이터를 분리하고 실제 토크나이저/그래프 호환성을 검사합니다.
5. 실제 모델 라우팅은 저장소 선택과 별도 평가합니다. 동일 코딩 작업의 성공률·실패 복구·재시도·총 사용량을 포함해야 합니다. 지금 수치로 구독 절감률을 주장할 수 없습니다.

현재 권장 범위는 **키워드 preview를 먼저 연결하고 Laya는 측정용 옵션으로 유지**하는 것입니다. 자동 작업 배정이나 현재 Codex 대화의 모델 전환은 구현하지 않았습니다.

# 작업 분할 판단 preview 설계

[English](decomposition-preview.en.md) · [추적 이슈 #11](https://github.com/teamswyg/laya-tools/issues/11)

상태: 설계·학습 준비 단계. 분할 CLI, 분할용 학습 모델, 자동 실행기는 아직 없다.
어려운 작업이 분할 가능하다는 뜻은 아니며, 분할 가능해도 비용이 줄어드는 것은 아니다.

## 생성과 결정을 구분하기

| 역할 | 입력 → 출력 | 담당 |
|---|---|---|
| 계획 생성 | 요청·저장소 근거 → 하위 작업, 계약, 의존성, 검증 계획 | 기존 생성 에이전트 또는 정해진 템플릿 |
| 계획 판단 | 요청·후보 계획·근거 → 정해진 선택지별 점수 | 별도 평가·학습한 Laya |
| 실행 정책 | 구조 검사·점수·보정·예산 → 허용/보류, 실행 가능한 작업 | Go |
| 작업 수행 | 하위 작업·필요한 문맥 → 코드·테스트·산출물 | 배정된 생성 에이전트 |
| 완료 확인 | 결과·테스트·원래 요구사항 → 검증 결과 | CI와 실행 하네스 |

Laya는 후보에 점수를 매긴다. 후보 계획, 코드, 자유 형식의 설명을 생성한다고 표현하지 않는다.
출력의 이유 코드는 Go 검사 결과와 명시된 근거에서 만들며 모델의 숨은 추론처럼 표시하지 않는다.
작업 성공 여부도 Laya가 선택한 `done` 라벨로 확정하지 않는다.

## 판단 대상과 인터페이스 초안

처음에는 원요청만 보고 무한히 분할안을 찾지 않는다. **주어진 후보 계획의 실행 방식**을 판단한다.
후보가 없거나 근거가 부족하면 `needs_context`이며, 이것은 원요청 자체가 분할 불가능하다는 뜻이 아니다.
`keep_atomic`도 모든 가능한 분할안을 부정하지 않고 현재 계획보다 원작업 유지가 적합하다는 뜻이다.

입력 필드는 다음과 같다. 아직 공개 API가 아니며 이름은 구현 시 확정한다.

- `schema_version`, `task_id`, `repo_revision`, `request`, `constraints`, 원요청의 `acceptance_criteria`.
- `candidate_plan.tasks[]`: 안정된 `id`, 목적, `depends_on[]`, 입력/산출물 계약, 읽기/쓰기 자원, 작업별 검증 방법, 요구사항과 연결된 ID.
- `evidence[]`: 공개 가능한 근거 ID, 출처 revision, 범위, 관측 사실. 모델 입력은 명령이 아닌 데이터로 취급한다.
- `budget`: 최대 분할 깊이·작업 개수·동시 실행 수·모델 호출·시간·추정 사용량. 알 수 없는 비용은 0으로 간주하지 않는다.
- 입력과 근거의 잘림 여부. 긴 계획을 조용히 잘라 판단하지 않고 중요 근거가 빠지면 보류한다.

출력은 `model_choice`, 선택지별 `probabilities`, `policy_decision`, `accepted`, `reason_codes[]`,
입력/모델/보정 버전, 구조 검사 결과와 잘림 표시를 분리한다. 정책이 모델 결과를 거절한 기록을 보존한다.
확률은 실제 성공 확률로 보장되지 않는다. 미지원 언어·분포 변화·낮은 보정 신뢰도에서 보류한다.

| 선택지 | 판정 기준 | 예시 |
|---|---|---|
| `keep_atomic` | 현재 후보로 나누면 불변식·검증 가능성·효율을 해침 | 한 트랜잭션의 원자성을 여러 구현 작업으로 분리 |
| `split_sequential` | 유용한 분할이지만 중간 산출물이나 공유 상태에 순서가 필요 | 계약 확정 → 구현 → 통합 검증 |
| `split_parallel` | 적어도 한 실행 구간에서 독립 작업을 동시에 진행 가능 | 인터페이스가 고정된 서로 독립 모듈 |
| `needs_context` | 후보·의존성·수용 기준·근거가 불충분 | 공유 DB 변경 영향이 알려지지 않음 |

혼합 DAG에서는 준비된 독립 노드만 병렬 실행한다. `split_parallel`은 모든 작업을 동시에 실행하라는 명령이 아니다.
파일이 다르더라도 같은 API 계약·DB·설정·생성물·외부 서비스를 공유하면 충돌할 수 있다.

## Go 정책의 처리 순서

1. 입력 크기·스키마·ID 중복·없는 의존성·자기 참조·순환을 검사한다. 잘못된 계획은 오류이며 모델 호출로 고치지 않는다.
2. 필요한 계약·검증·근거가 없거나 중요한 입력이 잘렸으면 `needs_context`로 보류한다.
3. 의존성의 도달 관계와 알려진 읽기/쓰기 자원 충돌을 검사한다. 공유 읽기는 허용 가능하지만 쓰기/읽기 및 쓰기/쓰기는 순서나 격리가 필요하다. 서로 다른 worktree만으로 외부 상태가 격리되지는 않는다.
4. 구조적으로 유효한 후보에만 Laya를 호출한다. 독립 보정셋에서 정한 선택지별 gate로 결과를 수용할지 결정한다. 별도 정책이 거절한 병렬 제안을 자동으로 순차 계획으로 바꾸어 실행하지 않는다.
5. 준비된 노드만 제한된 동시성으로 전달하고 각 노드의 난이도/모델 라우팅은 별도로 수행한다. 미리 지정한 모델·기존 보류 동작을 존중한다.
6. 하위 검증 후 원요청의 통합 검사를 수행한다. 실패 시 수정/재계획은 남은 예산 안에서만 허용한다.

초기 preview 정책 후보는 깊이 2, 총 8개 하위 작업, 동시성 2, 재계획 1회다. 이는 성능 근거가 없는
실험용 상한이며 제품 기본값이 아니다. 동일 계획 반복, 산출물 진전 없음, 예산 소진은 중단 조건이다.
타임아웃은 실패/미완료로 남기고 성공으로 세지 않는다. 구조 검사는 의미상 독립성이나 요구사항 충족의 증명이 아니다.

## 학습과 평가

분할 방식과 난이도는 별도 판단 과제로 시작한다. 선택지별 분류 손실로 먼저 baseline을 만들며,
생성 모델의 다음 토큰 예측 학습이나 긴 사고 과정 생성 데이터를 그대로 가져오지 않는다.
원본 학습의 RLCD까지 복제하는 것은 첫 MPS smoke 성공 조건이 아니다.

공개/자체 작성 원요청과 후보 계획을 묶고, 잘못된 분할도 포함한다. 예를 들어 숨은 공유 자원,
필수 통합 검사 누락, 장황하지만 쉬운 일, 짧지만 원자적인 변경, 문맥 부족, 토큰 초과다.
같은 원요청의 좋은/나쁜 계획·번역·바꿔 쓴 문장은 같은 데이터 분할에 둔다. 선택지 순서 변경에도 답이 일관적인지 검사한다.
기존 36개 난이도 회귀 사례를 분할 평가용 정답으로 재활용하지 않는다.

- 1차: 혼동행렬, 위험한 병렬 제안의 오수용, accepted precision/coverage, class recall, Brier/ECE, 언어·길이별 결과.
- 2차: 같은 작업에 대해 **분할 없음**, **규칙만 사용**, **생성 계획+Laya 판단** 비교. 생성 모델의 계획 평가를 비교군으로 추가할 때는 비용도 포함한다.
- 성공·누락·통합 실패·재시도와 총 사용량/시간을 함께 측정한다. 계획 생성·문맥 반복·모델 상향·실패 복구 비용을 빠뜨리지 않는다.
- 초기 public fixture 16→32→64개는 개발 단계별 목표이지 정확도 보증이 아니다. 최종 평가셋은 따로 고정하고 구간 추정과 표본 수를 기록한다. 충분한 근거 전까지 자동 실행을 기본으로 켜지 않는다.

## 외부 근거 검토 (2026-09-30)

아래는 방법론 참고이며 upstream 코드를 복사한 구현이나 우리 성능의 증거가 아니다.

- [Laya 공식 모델 카드](https://huggingface.co/convaiinnovations/laya): 선택지 기반 결정 구조이며, zero-shot 한계와 도메인 학습·보정 필요를 명시한다. 따라서 모델 이름만으로 분할 능력을 가정하지 않는다. 원본 영어 모델과 multilingual은 별도 평가하며 한국어 정책 보류를 임의로 해제하지 않는다.
- [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents): 생성 오케스트레이터의 동적 작업 분할과 분류 라우팅, 독립 작업 병렬화를 구분한다. 문서 자체가 도구 생태계 변화도 알리고 있으므로 구조 원칙만 참고한다. 우리는 계획 생성과 판정의 책임을 분리하고 코드 검사 및 중단 조건을 둔다.
- [RouteLLM](https://arxiv.org/abs/2406.18665): 모델 간 품질·비용 절충을 선호 데이터로 학습하는 연구다. 분할 알고리즘의 증거는 아니다. 우리에게 필요한 시사점은 사람이 붙인 난이도가 최적 모델의 정답은 아니며 실제 결과 기반 레이블로 발전시켜야 한다는 것이다.
- [On Calibration of Modern Neural Networks](https://arxiv.org/abs/1706.04599): temperature scaling은 보정 baseline 후보다. 보정으로 잘못된 순위나 새로운 도메인의 정확성이 보장되지는 않으며 학습/보정/최종 평가를 분리한다.
- [PyTorch MPS](https://docs.pytorch.org/docs/2.14/notes/mps.html): MPS 장치와 실제 텐서 실행을 검사할 근거다. 작은 텐서 backward 성공, Laya backward 성공, 라우팅 품질 개선은 각각 다른 완료 단계다.

검토 결론: **생성 에이전트가 제안하고 작은 결정 모델이 평가하는 방향은 유지한다.** 가장 약한 전제는
작은 모델이 문맥에서 드러나지 않은 의존성을 알아낼 수 있다는 가정이다. 근거 수집·구조 검사·보류와 실측 비교를
먼저 갖추고, 같은 품질에서 총 비용이 줄지 않으면 규칙 기반이나 기존 실행을 유지한다.

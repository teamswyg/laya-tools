# 라우터 기획: 코딩을 맡기기 전에 작업의 난이도를 분류한다

Laya는 코드를 작성하는 모델이 아니다. 짧은 입력을 읽고 주어진 선택지 중 하나를 고르는 작은 모델이다. 여기서는 “빠른 모델 / 보통 모델 / 강한 모델 중 어느 것이 필요한가?”를 판단한다. 실제 코딩은 사용자가 쓰던 Codex가 맡는다.

흐름은 `사용자 요청 → 로컬 Laya 판단 → 선택 정책 → Codex 새 세션`이다. 선택 정책은 Laya 답변을 그대로 믿지 않는다. 확신도가 0.9 미만이거나 입력이 잘렸거나 한국어처럼 검증되지 않은 조건이면 강한 모델을 유지한다. 사용자가 모델을 명시하면 그 선택이 가장 우선한다.

예를 들어 주석 오타 수정은 빠른 모델 후보, 한 함수의 일반적인 버그 수정은 보통 모델 후보, 여러 파일에 걸친 동시성 장애는 강한 모델 후보다. 이것은 분류 기준의 예시이며, 실제 모델이 항상 이렇게 맞춘다는 뜻은 아니다. 현재 분류기는 전용 난이도 데이터로 학습/보정하지 않은 초기 실험이다.

두 방식으로 쓸 수 있다.

- `riidolaya route`: 추천 결과만 확인한다. Codex에 아무 변화도 주지 않는다.
- `riidolaya codex`: 추천 결과로 새 Codex CLI 작업을 시작한다. 진행 중인 대화의 모델을 바꾸지는 않는다.

모델별 실제 이름은 사용자가 정한다. 모델 목록이나 요금이 바뀌어도 도구를 다시 배포할 필요가 없다. 강한 모델 이름을 비워두면 원래 Codex 기본값을 유지한다. 로그인과 API 키를 읽거나 별도로 저장하지 않는다.

코드 검색은 독립 기능이다. 저장소 전체를 큰 모델에게 읽히는 대신 키워드로 후보를 뽑고 Laya가 관련성을 평가하여 몇 개의 코드 구간과 줄 번호를 돌려준다. 이 결과를 Codex가 이용하면 읽는 양이 줄 수 있다. 그러나 원래 검색이 잘 되던 작업에서는 Laya 호출이 추가 지연만 만들 수 있다. 그래서 `--lexical` 비교 모드를 제공한다.

사람은 CLI 출력으로, 에이전트는 JSONL 또는 MCP로 사용할 수 있다. JSONL/MCP 모드는 모델을 한 번만 로드하여 다음 요청에 재사용한다. 네트워크 서버나 macOS 자동 실행 서비스 설치는 기본 동작에 없다. 연동은 명시적으로 선택한다.

실제 비용 절감은 아직 증명하지 않았다. 작은 모델이 실패해서 다시 강한 모델로 풀어야 한다면 비용이 더 들 수 있다. 다음 평가는 동일한 코딩 과제를 고정하고 성공률·총 사용량·걸린 시간·재시도 횟수를 함께 비교해야 한다. 현재 구현은 로컬 검색/추론 측정과 안전한 추천 정책까지이며, 작업 완료 여부를 판단하는 자동 재시도 루프는 아직 없다.

개발 변경의 검토는 CI에 맡긴다. 테스트와 정적 검사, 실제 추론 검사, 비밀정보 검사가 통과해야 병합한다. 사람 리뷰 승인은 요구하지 않는다. 이는 도구 개발 과정의 승인 정책이며, 사용자의 Codex 실행 권한을 풀어버리는 설정은 아니다.

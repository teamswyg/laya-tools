# 코드 동작에서 학습 정답을 만드는 방법

작은 모델이 확인할 후보의 순서를 제안하려면, 먼저 후보가 실제로 어떤 동작을 하는지 알아야 합니다. 이번에는 공개 Go 코드의 동작을 확인하고, 같은 요청에 대해 동작이 다른 후보를 만들어 학습 자료 3개를 추가했습니다. 모델 학습과 실제 사용 비용의 개선 여부는 다음 별도 실험에서 확인합니다.

## 실제로 확인한 내용

| 검사 | 결과 | 해석 |
|---|---|---|
| 시간 변환과 명령행 슬라이스 처리 | 고정 입력 32건 모두 사전 기대값과 일치 | 오류 원인, 시간 값, nil·빈 슬라이스와 변경 상태를 구분했습니다. 아직 학습 요청으로 전환하지 않았습니다. |
| UUID 파싱·상태 변경과 영어 서수 후보 | 후보 9개 × 입력 8개, 총 72건 모두 사전 기대값과 일치 | 맞는 후보와 일부러 다른 동작을 하는 후보를 모두 실제로 실행했습니다. |
| 학습 정답 검토 | 요청 3개, 정답 후보 3개·오답 후보 6개 | 코드의 요청 만족 여부와 설명의 충실성, 관찰 항목의 완결성을 따로 확인했습니다. |

“기대값과 일치”는 코드가 좋은 후보라는 뜻이 아닙니다. 예를 들어 잘못된 후보가 오류를 버릴 것이라고 미리 예상했고 실제로 오류를 버렸다면, 관찰 검사는 통과하지만 사용자 요청에는 틀린 후보입니다.

## 어떤 차이를 학습시키나

| 요청 | 정답 후보 | 오답 후보에서 확인한 차이 |
|---|---|---|
| UUID 오류를 반환하고 파서의 부분 결과도 유지 | 원 파서의 결과와 오류를 그대로 전달 | 오류 때 결과를 0으로 바꾸거나, 오류 반환 대신 패닉을 냅니다. |
| nil·빈 값·오류 때 기존 UUID 상태를 유지하고 오류를 반환 | 기존 상태에서 스캔하고 오류를 전달 | 스캔 전에 상태를 지우거나, 오류를 버립니다. |
| 영어 서수에서 11·12·13으로 끝나면 `th` 사용 | 원 서수 함수의 규칙을 유지 | 끝자리만 보고 `11st`를 만들거나, 항상 `th`를 붙여 `1th`를 만듭니다. |

오답 후보의 설명도 그 코드에 충실해야 합니다. “오류를 버린다”는 설명이 실제로 오류를 버리는 코드를 가리킬 때 학습에 사용할 수 있습니다. 설명이 코드와 맞지 않는 사례는 정답 판단과 별도로 다룹니다. 정답은 설명의 유사도에서 만들지 않고 고정한 요청, 소스와 실제 동작에서 만들었습니다.

이번 정답은 요청마다 고정한 8개 입력과 해당 소스 버전에 연결됩니다. 모든 가능한 입력에 대한 실험 증명은 아닙니다. 코드·설명을 함께 읽은 AI 보조 검토이며, 독립적인 사람의 맹검 검토도 아닙니다.

## 다음 학습에서 바꾸는 것

기존 76개 요청의 문장, 후보 순서, 정답, 학습 제외 표시와 역할을 유지합니다. 새 3개는 학습 쪽에만 추가합니다. 같은 UUID 소스의 파싱·스캔과 그 변형은 한 그룹에 묶고, 서수 함수와 그 변형은 다른 그룹에 묶습니다. 전체 자료의 역할을 다시 추첨하지 않습니다.

새 구성은 요청 79개·후보 235개입니다. 이 자료를 Go 학습 입력으로 변환하고 기존 부분이 그대로 유지되는지 확인하는 단계는 아직 실행하지 않았습니다. 다음 모델은 기존 첫 FP32 모델과 같은 설정으로 처음부터 학습하는 형제 실험입니다. 데이터 추가 효과를 먼저 보므로 이번에는 시드, 특징 추출, 손실 함수와 양자화 방식을 함께 바꾸지 않습니다.

이 경량 실험은 직접 만든 Go 특징과 작은 모델을 사용합니다. 기존 Laya 본체의 파인튜닝이나 GPU 추론을 수행한 결과로 읽으면 안 됩니다. Laya 라우터와 연결하는 일, 3진 압축의 추가 실험, 모델 활성화는 각각 근거를 확인한 뒤 진행합니다.

## 시간과 메모리

32건 관찰의 전체 프로세스는 약 2.56초·최대 RSS 18.70MiB였습니다. 72건 후보 관찰은 약 2.84초·최대 RSS 18.63MiB였습니다. 각각 한 번 실행했고 자동 재시도는 없었습니다. 이 값에는 시작, 원문 확인, JSON 기록과 디스크 동기화가 포함됩니다. 모델 추론 속도나 함수 한 번의 메모리 사용량은 측정하지 않았습니다.

학습 준비의 기존 한도는 Go 힙의 완만한 256MiB 제한, 전체 프로세스 RSS 관찰 예산 256MiB, 외부 실행 제한 300초, 신규 데이터·모델·수치 기록 합계 64MiB입니다. 힙 설정이 OS 메모리를 강제로 제한하는 것은 아닙니다.

추가 저장 감사에서는 중복 저장본을 포함한 일부 자료만으로 67,943,460바이트를 확인했습니다. 이는 64MiB보다 834,596바이트 많고, 전체 합계의 하한입니다. 과거 누적 쓰기량과 현재 보존량을 원문 계획이 구분하지 않았으므로 새 학습 실행을 보류하고 저장 기준을 명시한 후속 계획을 검토합니다. 예산 초과 기록은 보존하며, 중복 파일의 해시가 같다는 이유로 사용량을 0으로 세지 않습니다.

## 결과를 판단하는 기준

기존 검증 자료와 네 단순 기준선을 그대로 비교합니다. 예상 확인 횟수가 가장 좋은 단일 기준선보다 5% 이상 줄고, 첫 후보와 상위 세 후보의 정답 포함률이 떨어지지 않아야 기존 개발 효용 기준을 통과합니다. 새 3개 자료의 결과는 학습한 자료에 대한 진단으로 따로 기록합니다.

기존 검증 결과는 이미 열람했으므로 새 학습의 결과도 개발 중 회귀 비교입니다. 별도의 새 의미 요청 2,400개 이상으로 만드는 최종 검증은 아직 갖춰지지 않았습니다. 72건의 후보 실행을 72개 사용자 요청으로 세거나 기존 79개를 최종 검증으로 사용하지 않습니다. 두 기존 학습 모델은 효용 검사를 실패해 기본값으로 활성화하지 않았으며 이번 관찰만으로 이를 바꾸지 않았습니다.

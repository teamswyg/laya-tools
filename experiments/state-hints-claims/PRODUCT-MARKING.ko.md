# 표시 계약의 제품 관점 검토 v1

2026-10-07 · 제품 기준 제안 · 사람 판정 미수집 · 운영 준비 완료 선언 아님

## 결론과 확인 범위

개발 댓글에서 답변 요청·현재 작업 보고·완료 보고를 저비용 Go 힌트로 찾는 목표와 세 주장 속성은 대체로 맞는다. 그러나 사용자에게 보이는 표식의 의미는 아직 확정되지 않았다. 첫 시험의 기본 단위는 **버전이 확인된 댓글의 주장**으로 제안한다. 작업 전체의 상태를 대표하는 표식으로 옮기는 판단은 별도의 어댑터 계약과 사람 기준이 필요하다.

확인한 출처는 공개 [issue155](https://github.com/teamswyg/laya-tools/issues/155), `experiments/state-hints-claims/RUBRIC.ko.md`·`.en.md`, `pkg/statehintclaims/model.go`뿐이다. issue의 현재 기록은 실제 연구 Fit 23회, 운영 합격 없음, 앱 쓰기 0회, 기본 OFF다. 최근 MLP의 사전 조건은 모두 실패했고 완료 정밀도는 24/32였다. 선형의 완료 제안 0건은 정밀도나 제품 성공의 근거가 아니다. private 원문·모델·평가 파일은 이 검토에서 읽지 않았다.

## 표식과 학습 라벨이 어긋나는 지점

| 사용자에게 보일 후보 | 현재 속성의 실제 의미 | 첫 시험에서 확인할 계약 |
| --- | --- | --- |
| ❓ 질문 | `response_requested`: 답변·설명·확인 결과·선택 요청. 물음표 없는 요청도 포함하고 응답 없는 명령은 자동 포함하지 않는다. | “응답 요청” 표식이 적합한가? 대상 수신자를 알 수 없으면 사람은 그래도 유용하다고 보는가? 문법적 질문과 동일한 라벨로 간주하지 않는다. |
| 🛠️ 진행 | `current_activity_claimed`: 식별되는 개발 작업이 현재 진행 중이라는 직접 보고. 제3자 활동도 포함한다. | 작성자의 보고인가, 실제 실행 관측인가를 구별하고 작업/하위 작업 범위를 붙인다. 오래된 보고를 현재 작업 상태로 읽지 않도록 이벤트 버전을 연결한다. |
| ✅ 완료 | `completion_claimed`: 작업 또는 하위 작업 완료·검증 완료 보고. 조심스러운 보고·직접 보고한 제3자 활동도 포함한다. | “완료 보고” 뜻이 사용자에게 전달되는가? 하위 검증 완료를 전체 작업 완료로 확대하지 않는다. 실행 성공 증거와 보고의 존재를 별도로 둔다. |

세 속성은 각각 true/false/unknown이며 함께 true일 수 있다. false는 긍정 주장 부재이지 작업의 미완료나 활동 부재가 아니다. unknown의 의미 불명확성과 낮은 확신·낮은 마진에 의한 보류는 로그에서 구분한다. 긍정 보고끼리 모순이면 주장 자체를 지우지 않고 충돌을 기록한다. 정정·철회는 문맥에 반영한다. 완료 뒤 댓글이 와도 자동으로 작업을 다시 진행으로 바꾸거나 완료를 취소하지 않는다. 새 응답 요청, 같은 범위의 정정, 다른 하위 작업 보고인지 각각 검토한다. 한 표식만 가능한 실제 catalog에서 세 양성을 어떻게 보일지는 사람이 확인할 사항이다.

## 첫 비공개 읽기 시험의 최소 입력

어댑터는 지정된 개발 작업과 기간의 새 댓글을 연속 수집하고 다음을 비공개로 보존한다. 첫 30–50댓글은 절차와 표시 기준을 확인하는 제안 규모이며 새 합격 문턱이 아니다.

- 원본 댓글 본문과 검증된 전체 본문 추출 결과, 언어, 댓글 식별자·작성자 식별자(로컬 가명 가능), 작성 시각. 코드·인용을 구분할 경계 정보가 있어야 한다.
- 팀·작업 식별자, 작업/하위 작업의 최소 범위 설명, 작성자·수신자의 해당 작업 관계, 필요한 직전 대화와 reply 대상. 관계를 모르면 그 필드를 미확인으로 남긴다.
- reader 출처, 전체 opaque revision/event version, 수정·삭제 여부, 수집 시각과 본문을 같은 revision에 묶는 검증. 분류 후 바뀐 본문은 새 댓글 버전으로 처리하며 오래된 결과의 부착 후보를 버린다.
- 검토 대상의 현재 catalog에서 “응답 요청/활동 보고/완료 보고”를 표현할 수 있는지, 댓글/작업 중 어디에 표식이 놓이는지. 실행·테스트 결과가 있다면 출처·시각·대상 범위를 별도 사실 필드로 보존한다. 그것이 없다고 완료 보고를 false로 바꾸지 않는다.

현재 모델의 `Scores`/`Predict` 입력은 text뿐이며 provenance·event facts·task state는 숫자 특징에 들어가지 않는다. 위 문맥은 **어댑터·사람 검토**의 입력이다. 현재 모델이 작성자·작업 범위·요청 수신자·근거 구간을 이미 출력한다고 가정하지 않는다. 필요한 필드가 없는 이벤트는 해당 연동 증거가 부족한 것으로 기록하며, 모든 의미를 unknown으로 덮어 성공을 주장하지 않는다.

## 로컬 기록과 사람 참고 판정

수집 전에 표식의 이름·단위·복수 표시 처리와 시험 기간을 기록한다. 작업을 아는 사람이 예측을 보기 전에 세 속성 각각의 true/false/unknown, 작성자 귀속·범위·근거 구간, 표식의 유용/불필요/오해 가능 및 이유를 기록한다. 가능하면 두 번째 사람이 독립 검토하고 원판정과 이견을 보존한다. 사람이 참여하지 않은 항목은 human_pending으로 남긴다. AI 재판정만으로 사람 참고나 제품 효용을 주장하지 않는다.

일반 로그는 원문 없이 로컬 event 가명, revision 결합 여부, model/rubric 버전, 세 winner/state/confidence/margin/unknown_reason, 제안·보류·충돌·무효화 이유, 읽기·추출·추론의 시간/자원, 사람 판정 유무를 담는다. 원문·근거 구간·진짜 IDs는 접근 제한된 로컬 참고 파일에만 둔다. 같은 thread/task와 번역쌍은 연관 사례로 묶고 사람 자료와 연구 자료의 노출 이력을 기록한다. 새 보정·최종시험 봉인을 열거나 이미 노출한 평가를 선택·오류 튜닝에 재사용하지 않는다.

.9 confidence/.05 margin은 그대로다. 제안 정밀도·지지 수를 언어/속성별로 분모와 함께 보고하고 true recall, coverage, 도움 된 제안 수, 누락·오해 비용을 함께 본다. 전부 보류는 제품 성공이 아니다. issue의 기존 계획에 있는 완료 정밀도 .98, 의도·언어별 최소 5사건/2선언계보, 오류 비용 10/3/1과 보류 기준은 변경하지 않는다. 해당 수치는 기존 판정 계획 출처이며, 숫자 통과나 선언 ID만으로 이번 세 속성의 운영 자격·독립성이 자동 입증되지 않는다.

## 선택 가능한 다음 시험

| 선택 | 비용과 장점 | 얻는 근거와 한계 |
| --- | --- | --- |
| A. 고정 text-only 모델의 비공개 댓글 shadow | 가장 작은 시작. 새 연속 댓글의 모델 제안을 사람이 비교하며 확신도 문턱 유지. | 실제 문체에서 주장 검출·보류·오해·커버리지 확인. 문맥 부족·작업 상태 판정·앱 연동 품질은 미해결. |
| B. 문맥 포함 읽기 어댑터 shadow | 작성자·reply·범위·revision을 붙여 사람이 같은 댓글을 text-only/문맥 포함으로 나눠 판단. 조회 비용 추가. | 어떤 누락 입력이 표시를 바꾸는지와 재생·수정·완료 뒤 reply 처리 확인. 더 좋은 새 모델이나 운영 쓰기의 증거는 아님. |
| C. 명시적 이벤트와 댓글 힌트의 병렬 비교 | 신뢰할 수 있는 완료/실행 이벤트가 이미 있으면 별도 사실 경로와 댓글 힌트를 비교. 계약 확인 비용 발생. | 보고와 사실의 차이, 추가 힌트가 필요한 영역 확인. 이벤트 없는 범위의 정답이나 전체 작업 완료를 대체하지 못함. |

A로 표시의 실용성을 확인하고 필요한 문맥이 확인될 때 B로 넓히는 순서를 제안한다. C는 기존 신뢰 이벤트가 확보될 때의 비교안이다. 이 검토는 공개 출처를 바탕으로 제안 문서를 작성했다. 이미 허용된 비공개 read-only shadow에 새 승인 절차를 만들 필요는 없다. 앱 자동 쓰기의 기본 OFF는 현행 연구 상태이며 사용자가 영구 금지했다고 해석하지 않는다. 추론 모델 라우팅·새 Fit·코드·앱 수정·실제 앱 적용을 이 검토의 완료로 간주하지 않는다.

근거·가정·사람 미확인 항목은 원문 없는 [계약 표](PRODUCT-MARKING.contract.csv)에 criterion ID로 구분했다. `established`는 출처에 명시된 계약/상태이고 `proposed`, `human_pending`, `integration_pending`은 확인 전 제안/미확인이다. 이 표에 사람 라벨·원문·성능 측정은 없다.

# 작은 속성 제안 준비56c 기록

[English](RESULTS-56c.en.md) · [사용법](USAGE-56c.ko.md) · [사전 설계](PLAN-56c.ko.md) · [준비 실행 계획](preparation-plan-56c.json) · [실행 snapshot](snapshot-56c.json)

Go `riido-scopeprep`으로 작은 속성의 제안 파일을 생성했다. 기존 부모4개에 속성3개를 붙인12행과 후보 설명36개이며 **모두 pending**이다. 후보 평가·공식 속성 정답·그룹·학습·모델 호출·순위·성능 측정은0이다. 이 결과를 새 모델의 효용이나 LLM 사용량 절감으로 해석하지 않는다.

## 왜 나누는가

전체 함수가 잘못됐어도 작은 속성에는 맞을 수 있다. 예를 들어 따옴표 안 쉼표는 올바르게 처리하지만 문법 오류에서는 부분 토큰을 남기는 함수가 있다. 전체 함수의 wrong 표시를 그대로 복사하면 “따옴표 안 쉼표를 보존하는가”라는 질문의 답을 잘못 만든다.

목표 사용자는 후보 코드의 검사 순서를 빠르게 정하고 싶은 에이전트다. 미래의 작은 모델은 좁은 질문에 힌트를 주고 독립 검증기가 실제 코드를 확인한다. 후보를 삭제하거나 실행을 승인하지 않는다. 현재 준비 도구는 그 후속 검증에 쓸 문구와 원천 연결만 만든다. 모델을 추천하거나 추론하지 않는다.

## 이번에 한 일과 분모

| 항목 | 실제 준비 기록 |
|---|---|
| 원래 부모 / 닫힌 함수 원천 | 기존56b의4개 / 4개, 새 독립 원천 없음 |
| 속성 | quoted comma, quote 밖 escape, syntax error의 zero output:3개 |
| 제안 / 후보 설명 | 12행 / 36개. 기존 후보3개씩 ID·순서·코드·closure 핀 보존 |
| 문구 검토 | 부모12개·후보36개 모두 pending; 독립 의미 승인0 |
| literal 정의 | 기존 독립 작성 literal9개를 좁은 기대값 표로 옮김; 새 독립 요청이 아님 |
| 공식 후보 평가·속성 라벨·그룹·역할 | 모두0 |
| 학습·모델 호출·순위·성능·보호 최종 접근 | 모두0 |

제안 행과 literal은 독립 골든셋 표본을 늘리지 않는다. 도메인별 서로 다른 보호 최종 요청 최소2,400개 목표는 별도다. 기존56b의 구분자 unknown4개, 72부모·전체17그룹·라벨16그룹과 전체 결과를 그대로 보존했다.

문구와 literal 의미가 일치하는지도 아직 승인하지 않았다. 특히 기대값 표는 유한한 지정 입력만 다루고 초안 문구는 더 일반적인 동작을 표현하므로, 후속 의미 검토에서 이 범위를 맞춰야 한다. 단순 길이 검사를 의미 검토로 취급하지 않는다.

## 고정한 코드로 생성

기존56b [PR79](https://github.com/teamswyg/laya-tools/pull/79)는 이후 `0d7edadadb6c8cbea66c56e40e3ab8b888f9bf65`로 자동 병합됐다. PLAN-56c에 남긴 CI 진행 중·문구 길이 검사 미실행 표현은 최초 설계 시점의 snapshot이다. 이번 구현 검사와 제안 생성은 이 후속 기록에서 구분한다.

준비 코드·검사·문서·[기계 계획](preparation-plan-56c.json)을 `daa8730949928c6158ceb02fd9be57952645b663`에서 먼저 고정한 뒤, Go1.27.1·CGO0·trimpath 실행 파일로 **준비 snapshot을1회** 생성했다. 재시도0, 종료0, stdout은 preparation 파일과 byte 단위로 일치한다. 준비 단위 검사와 제안 생성 검사는 이 고정 전에도 실행했다. 이 경계를 공식 속성 감사의 봉인으로 부르지 않는다.

23개 코드·검사 파일, 기존27개 보존 핀과 문서6개를 대조했다. 실제 컴파일 원천19개와 디스크 파일도 일치한다. 기존 JSON 파일 SHA 확인에 더해, factory가 재구성한 **원본 전체**를 같은 들여쓰기 JSON+끝줄바꿈으로 해시 검증한다. 요청·후보 순서·코드/closure 핀·선택 밖 부모가 달라도 거절한다.

## 검사와 한계

전체 Go race·vet, CGO0 policy packages, 포맷, 오프라인 publication4개·PDCA8개 검사와 redacted 보안 검사가 통과했다. 독립 읽기 검토는 원본 연결·정확한 오류 종류·문구 pending·후보 보존·특징 분리를 확인했다. 저장소 PR의 실제 CI·병합 상태는 PR checks에서 확인한다. 이 글을 작성한 시점에는 새 PR의 CI 완료를 주장하지 않는다.

Snapshot 생성 후 공개 기록 CI 검사를 별도로 추가했다. 고정 계획·23개 구현/검사·기존27개 핀·문서6개·19개 컴파일 원천과 공개 산출물 SHA를 확인하고, 제안 구성 바이트를 재생한다. 이 검사는 새 공식 실행·정답 관측·독립 표본을 추가하지 않는다.

관측 어댑터 단위 검사는 기존 네 함수의 실제 반환을 확인한다. 성공의 OK0과 문법 오류 Syntax1을 정확히 구분하고, syntax literal은 Count0·전체8토큰 비움·no-panic을 함께 요구한다. 오류 보고를 생략한 구현도 통과하지 못한다. **이 준비 단위 관측과 prepare 명령의 공식 후보 평가0은 다른 범위**다. 아직 속성별 acceptable set이나 answerable/no-answer/unknown 분류를 생성하지 않았다.

JSON·출력·원천 크기는 제한하고 기존 출력은 덮어쓰지 않는다. GOMAXPROCS1과 Go heap256MiB soft limit은 설정이다. 이번 전체 RSS·CPU 사용량·지연·GPU 사용은 **미관측**이며, 속도나 메모리 개선 수치를 주장하지 않는다. 해시 검증은 문장 충실성·학습 효용·원천 다양성의 증거를 대신하지 않는다.

## 다음 단계

문구의 유한 literal 범위와 출력 계약을 맞춰 별도 버전으로 고정하고, 공식 속성 감사 계획을 결과 전에 봉인한다. 부모·형제 속성·모든 양성/음성 후보·shared helper를 함께 묶어 분할 누수를 막는다. 다양한 공개 개발 원천120→240과 역할·무학습 효용 계획을 먼저 준비하며 최소15그룹·최소5% 효용 필요조건을 낮추지 않는다. 그 전에 fits0을 유지한다.

[56d 상주 자원 사전 계획](PLAN-RESIDENT-56d.ko.md)은 별도 미실행 제안이다. 24children·timed24,576회는 반복 타이밍 관측의 예정 개수이며 독립 요청이나 실제 측정이 아니다. 첫 응답·pipe·controller·child CPU/RSS를 구분해 측정한 뒤 캐시·lock·SIMD·SoA 적용 여부를 판단한다. 새 가중치가 없어 Hugging Face 모델 버전을 발행하지 않았으며 기존 계보·불변 참조를 유지한다.

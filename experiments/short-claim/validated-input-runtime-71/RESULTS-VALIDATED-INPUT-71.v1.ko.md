# 검증된 입력 재사용: 공개 fixture 측정

기존 CLI는 입력을 읽으며 검증·정규화한 뒤, 순위 계산에서 같은 입력을 다시 검증·정규화했다. 새 `ValidatedInput`은 검증된 고정 배열과 문자열을 비공개 필드로 보관한다. 생성자는 기존 검증을 그대로 사용하며, 순위 계산은 기존 토큰화·점수·정렬 함수를 재사용한다. 영 값은 거절하고, 외부로 반환하는 `Prepared`는 값 복사라 내부 상태를 바꿀 수 없다. 공개 `Rank(Prepared)`와 `Baselines`는 기존 검증을 유지한다. 이 타입은 형식·정규화 계약을 나타내며 내용의 진실성이나 실행 권한을 보증하지 않는다.

네 가지 baseline의 순서·점수·fallback 및 CLI 스키마·입력 digest 동등성을 확인했다. 잘못된 생성자 입력, JSON으로 위조한 영 객체, 변경된 `Prepared`, 원본 slice와 반환된 복사본의 변경, 동시 읽기 및 기존 stream 경계·오류 개인정보 테스트도 통과했다. Go 1.27.1 대상 패키지 race와 vet를 각각 한 번 실행했다. 새 map·lock·모델·학습·SIMD는 추가하지 않았다.

측정은 기존 공개 8후보 fixture의 `lexical_ordered`, 10,000회 반복, CPU 한 개, Go 메모리 soft target 256 MiB를 사용했다. 한 번 빌드하고 한 번 측정했으며 재시도는 없었다. 새 프로파일과 새 pprof 읽기는 0회다.

이전 측정은 CPU 프로파일을 사용했고 새 측정은 사용하지 않았다. 각각 한 표본이며 주변 호스트 부하·스케줄링은 기록하지 않았다. 부모의 전체 검사는 새 측정 완료 통보 후 시작하도록 조율했으나 다른 동시 작업의 부하는 관측하지 않았다. 따라서 지연시간을 최적화만의 인과적 속도 향상으로 승인하지 않는다. 종료 HeapAlloc은 오히려 증가했으며 강제 GC 없이 남은 쓰레기를 포함한다. 누적 할당·종료 heap·OS RSS는 서로 다른 지표이고, soft target은 OS hard cap이 아니다. GPU·native encoder·학습 모델 호출과 GPU 메모리 측정은 없다.

성공 경로의 소스 산술상 benchmark는 기존과 동일한 50,605개 stage callback을 수행한다. 검증 호출은 40,486→20,243, 정규화 호출은 364,374→182,187이다. 이는 동적 계측값이 아니며 첫 71 fit 실행의 횟수를 수정하지 않는다. 현재 공개 fixture의 처리 비용 측정으로 실제 76 validation 성능, 모델 품질, LLM 토큰·요금 절감은 입증하지 않는다.

구현·비교 helper는 같은 작성자의 검토이며 독립 품질 승인으로 부르지 않는다. 소스 원점은 `9d204c2c700505658c108297d5fa769a835a60c3`; 수정한 여섯 파일은 측정 전에 [소스 봉인](SOURCE-FREEZE-71.v1.json)했다. [비교 JSON](COMPARISON-VALIDATED-INPUT-71.v1.json)과 [실행 장부](ATTEMPT-LEDGER-VALIDATED-INPUT-71.v1.json)에 정확한 원본 bytes/SHA, 한계와 횟수를 기록했다. 원문 입력·바이너리·raw profile·raw 로그·호스트 경로는 비공개로 유지한다. 외부 게시·push는 이 작업에서 수행하지 않았다.

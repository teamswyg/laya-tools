# 요청 79개 실험 다음의 PDCA: 자료부터 넓히기

판단을 유지합니다. 작은 모델은 후보를 먼저 확인할 순서를 제안하는 주장·힌트 도구로 실험하고, 같은 79개 자료에서 seed·epoch·손실을 바꾸어 재도전하는 일은 멈추는 편이 좋습니다. 이번 실행이 실패했다는 것은 이 고정 실험에서 유용성을 얻지 못했다는 뜻이며, 모든 작은 모델이나 3진 학습이 불가능하다는 결론은 아닙니다.

## 실제로 확인한 것

기존 요청 76개에 학습 전용 요청 3개와 라벨 9개를 추가하고, 첫 FP32 실험과 같은 방식으로 한 번 학습했습니다. 기존 검증 20개 중 정답이 있는 요청 10개와 정답 없는 요청 5개를 평가했고, 알 수 없는 요청 5개는 제외했습니다. 가장 좋은 기존 비교군은 모의 검증 27회와 Top-1 정답 5/10이었습니다. 새 모델은 31회와 2/10으로, 첫 실험 71과 같은 합계입니다. 검증 BCE는 0.6657976915843424에서 0.6662350441005636으로 조금 나빠졌습니다. 이전 pair+BCE 실험 72도 33회·1/10으로 개선되지 않았습니다.

새 학습 요청 3개만 따로 보면 모델은 모의 검증 6회·Top-1 1/3이고, lexical 비교군은 4회·2/3입니다. 이 세 개는 학습에 사용한 자료이므로 일반화 평가가 아닙니다. 후보가 각각 세 개라 Top-3 3/3은 정답 후보가 세 후보 안에 있다는 정도의 숫자입니다. 이를 성능 개선으로 읽으면 안 됩니다. 검증 횟수는 저장된 정답으로 계산한 후보 확인 횟수이며 실제 Codex 호출·토큰·요금을 측정하지 않았습니다.

## 코드가 보여 주는 구조와 아직 모르는 원인

현재 `internal/hintlearn/learn.go`는 요청과 후보의 단어 및 인접한 두 단어를 만들고, 양쪽의 모든 교차를 부호 있는 8,191개 해시 칸에 넣습니다. 나머지 한 칸은 단어 겹침 비율입니다. 따라서 “상호작용 특징이 전혀 없다”는 설명은 틀립니다. 점수는 특징과 계수의 선형 합이며 언어 인코더나 문장 생성 과정은 없습니다. 조건절과 행동, 부정의 적용 범위, 멀리 떨어진 주체·대상의 연결을 명시적으로 보존하지는 않습니다.

새 단어 조합의 부족, 조건 관계를 표현하는 한계, 해시 충돌, BCE와 실제 후보 순서의 목적 차이는 가능한 원인입니다. 이번 결과만으로 그중 하나를 원인으로 확정할 수 없습니다. 현재 자료가 똑같은 특징으로 상반된 의미를 나타내는지, 또는 충돌 때문에 틀렸는지는 이 분석에서 특징을 다시 계산하지 않았으므로 미확인입니다.

`claimfit`은 unknown 라벨을 학습 행으로 만들지 않고, 명시적 마스크가 있는 행은 가중치 0으로 남깁니다. 가중치 0은 BCE와 데이터 gradient에 기여하지 않습니다. 첫 학습은 행 91개·양의 가중치 73개, 이번 학습은 100개·82개입니다. batch 128보다 둘 다 작으므로 epoch당 batch는 하나입니다. batch 수가 늘어난 탓이라는 설명은 맞지 않습니다. 코드의 가중치 정규화와 batch 나눗셈을 합치면 양의 가중치 합으로 평균하는 형태여서, 새 9개 신호와 기존 신호의 상대 비중이 함께 바뀝니다. 특징·정규화·부동소수점 누적의 개별 기여를 분리해 측정한 인과 실험은 아닙니다.

## 다음 세 경로의 우선순위

| 경로 | 지금 얻을 수 있는 것 | 한계 | 권고 |
|---|---|---|---|
| 새 의미 요청과 독립 계약 확보 | 모델이 배울 신호와 새 source-group 검증 자료를 늘린다 | 원문·권리·검사기 작성 비용이 들고, 수만 늘려서는 개선을 보장하지 않는다 | 주 경로. 다음 30~100개 중 목표 60개를 먼저 준비한다 |
| 조건·행동 관계 특징의 제한된 비교 | 표현 구조가 병목인지 검증할 가설을 만든다 | 이미 교차 특징은 있으며, 새 규칙이 작성자의 문법만 암기할 수 있다 | 병렬 준비만 한다. 새 개발 그룹에서 기본형과 한 가지 변경을 사전 고정해 비교한다 |

조건 특징의 첫 가설은 인접한 단어를 더 많이 넣는 것보다, 제한된 조건-행동-극성 정보를 보존하는 것입니다. 예를 들어 “오류면 상태를 보존한다”와 “성공이면 상태를 보존한다”를 별도의 관계로 다룹니다. 원문 밖의 원천 ID, 정답 라벨, 역할, 저장소 이름을 특징에 넣지 않습니다. 우선 새로 작성한 작은 개발 진단으로 표현 구분 가능성만 확인하고, 실제 개선 비교는 새 그룹과 고정 BCE 조건에서 한 번의 별도 실험으로 설계합니다. 아직 이 특징이나 새 학습을 구현·실행한 것이 아닙니다.

## 다음 배치: 목표 60개의 새로운 의미 요청

한 요청은 별도의 동작 계약이어야 합니다. 같은 함수의 입력 예시, CSV 행, 후보 수, 번역, 오류 문구 변경이나 같은 버그의 재서술은 새 요청이 아닙니다. 기존 79개와 원천 후보 120개를 대조해, 같은 의미 계약이면 기존 ID에 연결하고 “새 적격 계약”으로만 셉니다. 새 논리 요청 수와 새 적격 수를 따로 보고합니다.

다음은 확보 목표이며 현재 확보 60개라는 뜻이 아닙니다. 여섯 행동 구간에서 각각 서로 다른 계약 10개를 목표로 합니다.

| 구간 | 찾아볼 서로 다른 행동 |
|---|---|
| 문법·파싱 | 허용 문법, 숫자 범위, 구분자 인용, 빈 입력, 부분 결과 정책 |
| 오류 뒤 상태·소유권 | 실패 시 상태 보존, 성공 시 초기화, 복사 소유권, 별칭 분리, 중복 순서 |
| 설정·타입 변환 | 값 부재와 명시적 값, nil 대상, 변환 오류, 기본값 우선순위, 메타데이터 |
| 정확한 산술·표시 | 부호, 범위, 반올림, 단위 경계, 서식과 실제 값의 일치 |
| 제한된 파일·입출력 | 짧은 쓰기, 부분 읽기, 경로 범위, 교체 원자성, 자원 해제 |
| 취소·재시도·수명 | 취소 시점, 재시도 조건, 상태 전이, 종료 확인, 시간·횟수 한도 |

공개 원천 조사 53의 저장소들은 탐색 출발점입니다. Source82의 mapstructure/pflag/Go 원문 57개는 준비 자산이며 57개 요청이 아닙니다. Source81의 32개 입력 fixture나 네 행동 목표를 32개 새 요청으로 바꾸지 않습니다. UUID·humanize처럼 이번 학습에 들어간 원천 가족은 이후 새 저장소 일반화 검증에 넣지 않고 학습/개발 노출을 기록합니다. Cobra와 pflag의 의존, 표준 라이브러리 복사, 같은 버그·템플릿을 연결하면 저장소 여섯 개가 그룹 여섯 개라는 보장은 없습니다.

최소 여섯 개의 연결된 원천 그룹과 여러 저장소를 실제로 확보하고, 점수를 보기 전에 그룹 전체를 train/selection-validation/calibration으로 나눕니다. 가능할 때 3/2/1 그룹에 약 30/20/10 요청을 배정하되, 연결 관계 때문에 그룹이 합쳐지면 원천을 추가하고 수를 다시 고정합니다. 중간 30개는 확보 과정 점검이지 자동 학습 시작 기준이 아닙니다. 개발용으로 읽은 이 60개도 final이 아닙니다. 주장하는 각 도메인의 최소 2,400개 보호 final은 별도로 원천·후보·정답·권한과 비용 관측 조건을 확보해야 합니다.

적격 요청마다 공개 revision·최소 실행 closure·라이선스와 존재하는 NOTICE, 요청 의미, 후보의 충실한 설명, 유한 입력/출력/오류/상태·채널 검사, 허용 정답 집합과 no-answer/unknown을 고정합니다. 단순한 함수 동작 주장은 원본 native 동작과 독립 기대값으로 확인합니다. 코딩 변경 요청으로 확장할 때는 변경하지 않은 기준을 거절하고 별도 정상 구현을 수용하며 의도적 오답을 거절하는 검사도 필요합니다. 원본이 이미 만족하는 동작을 버그 수정 성공으로 기록하지 않습니다. 제한된 입력의 검증은 그 계약 범위의 증거이며 전체 입력 정확성 증명은 아닙니다.

## 사용자와 에이전트가 사용할 때의 경계

현재 경로는 짧은 Go 동작 주장과 후보 설명을 비교하는 작은 CPU 힌트 모델입니다. 후보 정답 라벨은 어떤 Codex 프로필이 작업을 성공시켰는지의 라벨이 아닙니다. 실제 model router에는 같은 요청에서 실행한 프로필의 독립 완료 결과와 실패·재시도·승격을 포함한 전체 비용이 필요합니다. 저장소 선택에는 접근 권한과 허용 저장소 집합, 분할에는 부모 작업의 통합 완료 결과가 따로 필요합니다.

연동은 선택 사항으로 유지하고, 제안은 후보 순서와 적용 범위를 반환하며 원래 검증과 fallback을 보존합니다. 점수는 보정된 성공 확률이 아닙니다. Bloom filter처럼 “정답을 절대 놓치지 않는다”는 성질도 없습니다. 후보를 영구 제거하거나 작은 모델로 강제 하향하는 근거로 쓰지 않습니다.

3진·INT8 형식은 별도 실험입니다. 현재 `Decode`가 FP64 계수 배열로 펼치는 경로에서는 작은 디스크 파일과 작은 실행 메모리가 같지 않습니다. 직접 packed scoring, 준비한 입력 재사용, 전체 요청 비용 측정이 있어야 초저자원 반복 사용의 이득을 말할 수 있습니다. GPU 추론, GPU 메모리 절감, SVD 효과를 이번 분석에서 관측하지 않았습니다.

## 2,400개를 처리하는 자원 계획도 별도로 필요함

현재 특징 자료는 이미 offsets·indices·values·labels·groups·weights가 나뉜 CSR 배열입니다. SoA 전환을 처음부터 해야 하는 상태가 아닙니다. 이 분리를 보존하면서 큰 float JSON과 반복 사본을 줄이는 일이 다음 자료 처리 계획의 후보입니다. SIMD가 빨라진다는 측정 결과는 없습니다.

실제 79개 변환의 소유 sparse payload는 2,207,317 B이고 결과 파일은 **5,369,450 B**입니다. 같은 요청당 밀도를 2,400개에 단순 비례시키면 각각 약 67,057,732 B와 163,122,532 B입니다. 이것은 가상의 계산이며 실제 규모 시험이 아닙니다. payload 예상치는 64 MiB보다 약 51,132 B 작지만 여유가 약 0.08%뿐이고 scratch·할당 오버헤드는 별도입니다. JSON 예상치는 현재 12 MiB 결과 한도를 크게 넘고 새 단계 총 64 MiB에도 맞지 않습니다. 이 고정 79개 전용 도구를 2,400개 전체에 그대로 적용하자는 제안은 아닙니다.

별도 버전에서 그룹 경계를 지키는 chunk 처리, binary CSR 또는 float 텍스트를 피하는 형식, 전체 단계·보관 경로 합계와 반복 추론 batch를 설계해야 합니다. chunk 수나 CSR 행 수를 의미 요청 수로 바꾸지 않고, 나눠 처리할 때도 기존 학습·모델·저장량 소비를 초기화하지 않습니다. 우선 다음 60개 요청을 적격 계약으로 확보하며 자원 용량을 준비하고, 이 분석에서 새 전체 Project를 실행하지 않습니다.

이 문서는 저장된 결과와 소스를 읽은 독립 후속 분석입니다. 새로운 Fit·Project·Features·Score·모델 Decode·원본 함수 실행·업로드는 모두 0회입니다. 변경하지 않은 검증 결과와 원문 지문은 동봉한 JSON에 있고, 다음 배치·특징 비교는 아직 제안입니다.

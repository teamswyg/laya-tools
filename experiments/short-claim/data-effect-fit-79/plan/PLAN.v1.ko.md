# 새 자료만 추가하는 FP32 학습 1회 — 조건부 준비안

첫 BCE 모델과 같은 방법으로 처음부터 새 형제 모델을 학습해, **자료 추가만으로 기존 개발 검증에서 후보 순서가 나아지는지** 확인한다. 아직 실행 계획이 동결되지 않았으며 학습·투영·특징 추출·새 정답·역할 배정은 모두0이다. [구조화 제안](PLAN.proposed.v1.json)에 현재 근거와 미정 입력을 분리했다.

추가 대상은 UUID Parse, UUID Scan, 작은 비음수 Ordinal 요청3개와 후보9개다. Parse와 Scan은 같은 UUID 가족이며 Ordinal은 별도 소스 가족이다. 원후보72회 유한 관찰, 반환/오류/패닉/상태 채널 검토, caption 충실성과 요청 조건의 설명 범위, 감독 정보 적격성이 먼저 확인되어야 한다. 현재 truth·acceptable·mask·weight·role은 null이다. 코드가 요청을 만족하지 않아도 caption이 그 잘못된 행동을 충실히 설명하면 음성 후보가 될 수 있다. 설명이나 관찰 근거가 부족하다는 이유만으로 음성으로 만들지는 않는다.

두 가족을 훈련에만 덧붙이는 안이다. 기존76개 요청·226개 후보의 문장, 순서, 정답, 마스크, 가중치와 실제70 역할은 유지한다. 전체21그룹을 새로 배정하면 기존 역할이 움직일 수 있으므로 하지 않는다. 실제 연결이 기존 가족으로 확인되면 그 역할을 따르며, 서로 다른 역할을 가로지르는 연결을 임의 분리하거나 옮기지 않는다. 과거 소스53/작업55 노출이 있으므로 신규 가족을 미노출·독립 검증 자료라고 부르지 않는다.

모두 적격일 때의 **계획치**는79요청·235후보·21가족, 훈련/검증/보정47/20/12요청이다. 훈련 행은91→100, 검증45행과 보정의 비학습 상태는 그대로다. 기존 unknown21요청·63후보는 null 감사 기록으로 보존한다. 기존 가중치0 행도 삭제하지 않는다. 신규9행의 마스크가 모두1이라는 조건에서 가중치0 행은 훈련18·검증1로 유지된다. 조건이 달라지면 실행 전에 별도 실제 입력 계약을 봉인해야 한다.

설정은 첫71과 동일하다: seed1729, FP32·8192차원, 최대50epoch, batch128, 학습률0.1, L2=0.0001, 가장 먼저 최소 검증 BCE가 된 epoch를 선택한다. pair λ=0이며 모델을 이어 학습하지 않는다. 이미 두 번 학습했으므로 원래 최대8회 중 이번 조건부1회가 세 번째다. 다른 seed·특징·임계값·caption을 탐색하지 않는다. 자료 증가 자체가 단어/정답 비율과 셔플·가중 배치 평균을 바꾸므로 특정 의미 조건 하나의 인과 효과라고 주장하지 않는다.

주 비교는 이미 노출된 기존 검증20요청 중 known/no_answer15요청·후보45개다. unknown5요청은 점수 비교 정답으로 쓰지 않는다. 마스크0 후보도 비교에서 빼지 않는다. 동일4개 control의 순서는 fixed_order→bm25→lexical_ordered→narrow_rule이며 동률 규칙도 고정한다. 기존 최선은27checks·Top1 5·Top3 10, oracle은21checks다. 같은 분모에서 기존5% 개선 기준은25checks 이하이며 Top1/Top3가 떨어지면 안 된다. 첫71은31checks, 두 번째λ1 모델은33checks로 실패했으며 기록을 유지한다. 새3요청의 control과 모델 결과는 훈련 출처 진단으로 따로 보고, 전체 검증에 섞거나3개만 따로 학습하지 않는다. 각 요청 후보가3개이면 Top3=3/3은 당연한 결과다. checks는 정답 후보 위치+1 또는 무응답의 전체 후보 수로 계산한 모의 검사수이지 실제 LLM/검증기 호출 수가 아니다.

구현은 기존76 loader의 parent-index→role-row 배열 연결과71 driver를 작게 버전 변경한다. 적격 새 입력과 두 가족의 train-only append manifest를 연결하고 기존76 prefix와 sparse 행의 index/value bits/labels/weights를 보존한다. 원래 claimfit.Project는 적격성을 승인하는 loader가 아니다. 조건부79 입력으로1회 투영하면 현재2단계 구현의 예상 특징 스캔은290회다. 이 수는 아직 실행한 수가 아니다. 미래 CI·source·binary·typed supervision·projection 핀은 root가 별도 동결한다.

CPU1·동시 학습1개, Go softheap256MiB, 전체 작업300초, sparse own payload64MiB, 신규 자료/모델/수치 기록 **합계64MiB**를 유지한다.256MiB RSS는 측정 후 예산 판단이며 기존 controller의 강제 OS RSS 제한은 false다. 기존71 writer에는 신규 파일의 누적 byte 검사가 보이지 않으므로 다음 실행에서 같은 합계 예산을 실제로 확인해야 한다. JSON 파일 크기·Go heap·own payload·OS RSS는 서로 다르다. 모델 계수와 본체는 Git에 올리지 않으며, 이번 준비에서 HF 게시나 기본 활성화는 하지 않는다.

이 실험에서 개선되어도 노출된 개발 자료의 회귀 결과다. 별도2400개 이상 신선한 의미 요청의 최종 검증은 아직 확보·열람·실행하지 않았다. 본인은 Source80/source-first와 Wanted72 작성자, 기존71 구현 및 결과를 본 비맹검 AI 보조 작성자이며 독립 정답 승인자가 아니다.

# 속성 제안 준비56c 사용법

[English](USAGE-56c.en.md) · [속성 사전 계획](PLAN-56c.ko.md) · [상주 자원 사전 계획](PLAN-RESIDENT-56d.ko.md) · [기존56b 결과](RESULTS-56b.ko.md)

`riido-scopeprep`은 작은 속성의 입력 제안을 만드는 Go 유지보수 도구다. 예를 들어 전체 함수가 올바른지 대신 “따옴표 안 쉼표를 보존하는가”를 별도 질문으로 준비한다. 이 명령은 후보를 실행하거나 순위를 매기지 않고, 정답도 부여하지 않는다. 기존 [riido-shortclaim](USAGE-56.ko.md)은 `unverified_heuristic` 상태로 후보 확인 순서만 제안한다. 어느 명령도 모델 선택이나 실행 승인을 확정하지 않는다.

공개 저장소 원천과 설치되거나 선택된 Go1.27.1이 필요하다. 저장소 루트에서 실행하며, 출력 폴더는 존재하지 않는 새 이름을 쓴다. Python·Laya 추론·GPU·인증 키는 사용하지 않는다. 실행 중 표준 라이브러리 원천 감사에 필요한 정보는 설치된 Go 또는 이미 캐시된 정확한 Go1.27.1에서 읽으며 다운로드는 비활성화한다.

```sh
mkdir -p .cache
go version
CGO_ENABLED=0 go build -trimpath -buildvcs=false -o .cache/riido-scopeprep ./cmd/riido-scopeprep
./.cache/riido-scopeprep --stage prepare --out .cache/my-scope-proposals-56c
```

`go version`이 Go1.27.1인지 먼저 확인한다. 임의 저장소 파일을 해석해 자동 정답을 만드는 기능은 없다. `--stage audit`도 지원하지 않는다.

| 생성 파일 | 의미 |
|---|---|
| `probes.json` | 기존 구분자 부모4개 × 속성3개 = 제안12행. 원래 후보3개씩의 ID·순서·원천 해시를 보존한 설명36개 |
| `preparation.json` 및 표준 출력 | 제안 바이트 해시, 실제 컴파일 원천19개, 개수·제한·중단 이유. 제안 문구와 정답의 독립 의미 검토 완료를 뜻하지 않음 |

모든 제안·후보 문구는 `caption_review=pending`이다. 길이 검사는 원문·정규화 각각512바이트와 정규화32단어를 확인하며, 넘는 문구를 자르지 않는다. Pending을 reviewed로 바꾸거나 코드·원래 부모·후보 순서·표 해시를 위조한 값은 라이브러리 검증에서 거절한다. `FeatureInputs`는 요청·후보 text만 순위 입력으로 투영하며 속성 ID·원래 부모·원천·정답 표는 특징에 넣지 않는다. 이 투영 자체는 의미 검토나 정답 인증이 아니다.

세 속성은 quoted comma 보존, quote 밖 escaped comma 처리, 지정된 문법 오류의 zero-output이다. 독립적으로 작성한 기존 literal9개를 좁은 표로 정의했고, 관측 어댑터의 준비 단위 검사에서는 기존 함수4개의 실제 반환을 확인한다. 전체 함수의 wrong 표시를 속성 정답으로 복사하지 않는다. 문법 오류 검사는 필요한 syntax 오류와 Count0·전체 토큰 배열의 비움을 함께 요구하므로 오류를 아예 보고하지 않는 후보가 잘못 통과하지 않는다.

Literal 표는 후속 코드 관측의 기대값이다. Pending 문구가 그 의미를 충실하게 표현한다고 승인한 것이 아니며, 공식 속성 라벨이나 answerable 분류도 아직 없다.

**준비 단위 검사와 이 명령의 실행은 구분한다.** `prepare` 명령의 후보 평가·정답 부여·그룹·역할·학습·모델 호출·순위·성능·protected final 접근은 모두0이다. 제안12행과 literal9개는 독립 골든셋 요청 수에 추가하지 않는다. 기존56b의 구분자 unknown4개와 전체 결과는 유지하며, 새 제안을 자동으로 known으로 승격하지 않는다.

이 문서와 제안 파일을 만든 것만으로 공식 속성 감사의 실행 계획·문구 검토·역할 분할이 봉인되지는 않는다. 문장 충실성과 다양한 원천, 별도 효용·역할 계획을 준비하기 전에는 학습하지 않는다. 도메인별 서로 다른 보호 최종 요청 최소2,400개 목표도 별도로 유지한다.

컴파일한 원천과 현재 파일이 다르거나 해당 패키지에 목록 밖 Go 구현 파일이 있으면 준비를 중단한다. 기존 입력 해시도 확인한다. 기존 출력 폴더와 파일은 덮어쓰지 않으며 오류는 입력·개인 경로를 포함하지 않는 고정 코드로 반환한다. Go heap256MiB는 soft limit이고 GOMAXPROCS1은 Go의 동시 실행 수다. 전체 RSS·OS thread·GPU hard cap이나 새 메모리·지연 측정으로 읽으면 안 된다. 원천 감사의 `go/types` 비용은 작은 상주 힌트 도구의 비용과 별개다.

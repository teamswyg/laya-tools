# JWT 정책 탐색 비용: 먼저 캐시와 단순 순서를 비교하기

작은 모델을 붙이기 전에, 반복하는 실제 작업을 캐시와 단순한 후보 순서만으로 얼마나 줄일 수 있는지 확인했습니다. 이 실험에서는 **같은 토큰의 서명 확인과 내용 해석을 재사용하면 고정 순서 탐색이 빨라졌습니다.** 반면 맞는 후보를 처음부터 검사하는 대조군은 재사용할 결과가 없어 캐시가 오히려 비용을 늘렸습니다. 모델 실행과 새 학습은 0회입니다.

## 무엇을 재사용하나

JWT는 서명된 토큰입니다. 여기서 claims는 토큰 안의 대상(audience), 만료·사용 가능·발급 시각 등의 내용입니다. 서명이 맞는지 확인하는 일과, 그 내용이 지금 검사하는 정책에 맞는지 확인하는 일을 분리합니다. 예를 들어 같은 토큰에 “alpha 또는 beta 허용”과 “alpha와 beta 모두 필요”를 비교할 때 서명 확인은 재사용할 수 있어도 정책 결과는 다시 계산해야 합니다.

캐시는 최대 5칸의 고정 배열이며, 각 요청·대조군·반복을 시작할 때 비웁니다. 토큰 전체, 공개 키 DER 전체, 서명 방식, 디코딩·claims 형식, 고정 소스 리비전이 모두 같은 항목만 재사용합니다. 처음 만난 토큰은 실제 `ParseWithClaims`로 서명과 디코딩을 확인한 뒤 저장합니다. audience 배열과 세 NumericDate 객체를 저장할 때와 다시 검사할 때 복사하고, 후보마다 새로운 `Validator`와 고정 시각을 사용합니다. 최종 `Token.Valid`와 정책 수락·거절 결과는 캐시하지 않습니다.

예상하지 않은 오류·입력 차이·캐시 변형·패닉·기한 초과는 **미확인(unknown)** 입니다. 이를 정책 거절로 바꾸거나 후보가 틀렸다고 간주하지 않으며, 해당 비용 탐색을 중단합니다. 이 동작은 고정된 공개 토큰, `RegisteredClaims`, 이번의 정책 옵션에 한정합니다. 다른 claims 구현이나 정책도 같은 방식으로 안전하게 재사용할 수 있다는 증명은 아닙니다.

## 첫 실행에서 확인한 결과

별도의 비용 실행을 한 번 했습니다. 먼저 원래 160개 판정 각각에 대해 매번 파싱하는 경로와 캐시 경로를 비교했습니다. **160/160쌍의 수락 여부·정규화한 오류 종류·claims 지문이 서로 같고, 이전 원본 판정과도 같았습니다.** 이 단계의 호출은 원본 경로 `ParseWithClaims` 160회, 캐시 인증 경로 20회, 새로운 정책 `Validate` 160회입니다.

그다음 요청 4개에 아래 네 가지 대조군을 적용해 3회 반복했습니다. `manual-first`는 결과 관측 전에 요청 계약에서 정한 첫 후보 `[4, 5, 2, 0]`을 사용합니다. 모델 예측이나 새로 학습한 순서가 아닙니다. 첫 입력 불일치에서 해당 후보를 그만 검사하고, 다섯 입력의 기대 수락과 모두 같은 첫 후보에서 탐색을 끝냅니다.

| 대조군 | 같은 순서로 3회 실행한 12개 요청 기록의 총시간 |
| --- | ---: |
| 고정 소스 순서, 캐시 없음 | 5.141583 ms |
| 고정 소스 순서, 캐시 있음 | 2.711623 ms |
| 미리 정한 후보 우선, 캐시 없음 | 2.428458 ms |
| 미리 정한 후보 우선, 캐시 있음 | 2.593877 ms |

표는 한 요청의 지연 시간이 아니라 **각 대조군의 요청 4개 × 반복 3회 합계**입니다. 캐시 조회·깊은 복사·옵션 준비·순서 구성·지문 검사와 나머지 요청 처리 비용을 포함합니다. 48개 탐색은 모두 같은 후보 `[4, 5, 2, 0]`에서 끝났고 미확인은 없었습니다.

고정 순서는 매 반복의 요청 4개 합계에서 43번 검사합니다. 캐시가 없으면 `ParseWithClaims` 43회, 캐시가 있으면 인증용 파싱 20회와 새로운 정책 검사 43회입니다. 23번의 재사용이 생겼습니다. 미리 정한 후보 우선은 처음 후보에서 끝나므로 캐시 유무 모두 파싱 20회이고 **캐시 적중은 0회**입니다. 캐시를 붙이면 조회·저장·복사와 별도 정책 검사만 추가됩니다.

## 모델을 위한 여유가 충분한가

캐시를 이미 적용한 상태에서 후보 순서만 바꿨을 때의 시간 차이는 반복마다 달랐습니다. 아래 값은 모두 요청 4개 합계이며, 양수는 미리 정한 순서가 빠르고 음수는 느렸다는 뜻입니다.

| 반복 | 고정 순서+캐시 − 미리 정한 순서+캐시 | 고정 순서+캐시 − 미리 정한 순서+캐시 없음 |
| --- | ---: | ---: |
| 0 | +61,497 ns | +107,457 ns |
| 1 | −44,209 ns | +66,125 ns |
| 2 | +100,458 ns | +109,583 ns |

마지막 열은 이번 입력에서 맞는 후보를 처음 검사하고 캐시를 생략하는 이상적인 대조군과의 차이입니다. **모델에 보장된 추론 예산이 아닙니다.** 모델을 사용하려면 특징 추출·추론·후보 순서 구성까지 포함해 실제로 이 차이보다 이득이 커야 하고, 맞는 순서를 예측하는지도 별도로 검증해야 합니다. 현재는 저렴한 비학습 검색 대조군을 먼저 추가하는 근거로 사용합니다.

모든 비용 반복은 160쌍 비교 뒤 같은 프로세스에서 실행해 코드와 런타임이 이미 사용된 상태였습니다. 가운데 반복에서 대조군 실행 순서를 뒤집었지만, 무작위 실험이나 독립적인 반복은 아닙니다. 공개 가상 토큰 13개를 요청 4개의 총 20개 입력 위치에서 재사용했습니다. 전체 JWT 계보의 노출된 `development_validation` 진단이며, 새 독립 작업 48개나 2,400개 평가를 확보한 것으로 세지 않습니다. 새 자료 편입·모델 활성화·학습·GPU·유료 호출은 없습니다.

## 시간과 메모리의 측정 범위

Apple M4 Pro의 macOS arm64, Go 1.27.1에서 실행했습니다. `GOMAXPROCS=1`은 Go 실행 슬롯 하나이며 OS 스레드 하나를 강제한 것이 아닙니다.

| 측정 | 관측값 | 포함하는 범위 |
| --- | ---: | --- |
| 요청별 작업 총시간 | 위 네 대조군 합계 | 요청 안의 준비·조회·복사·판정·결과 확인 |
| `main` 경과 시간 | 23.256416 ms | 입력 준비, 160쌍 비교, 48개 탐색; import 초기화와 출력 직렬화·쓰기는 제외 |
| 자식 프로세스 전체 경과 시간 | 608.614250 ms | 시작부터 입출력·대기 정리까지; 원본 응답 저장 시간은 제외 |
| 자식 프로세스 전체 CPU 시간 | user 29.161 ms + system 8.955 ms | 초기화·작업·출력을 포함한 OS 누계 |
| 자식 프로세스 최대 RSS | 14,532,608 B, 약 13.86 MiB | 모든 대조군을 실행한 프로세스 전체의 OS 최대값 |

전체 CPU·RSS를 캐시별 또는 모델별 사용량으로 나눠 측정하지 않았습니다. RSS는 Go 힙이나 캐시의 크기가 아니며, 두 경과 시간의 차이도 순수 시작 비용을 분리한 측정은 아닙니다. `GOMEMLIMIT=64MiB`는 부드러운 Go 메모리 목표이고 256MiB RSS 기준은 실행 뒤 검사입니다. 서명 검증의 내부 호출 횟수는 관측하지 않았습니다. 이전 원본 판정의 시간을 더해 절감량을 만든 것이 아니라 이번 실행 안의 대조군을 비교했습니다.

## 저장된 결과를 확인하기

저장된 첫 응답에서 결과 일치, 탐색 중단, 호출 수와 비용 합계를 다시 확인하려면 저장소 루트에서 실행합니다. 원본 JWT API·모델·학습을 다시 실행하지 않습니다.

```sh
go run ./experiments/short-claim/next-cohort-jwt-audit/cost-replay
```

새 원본 실행을 원하는 경우에만 아래 별도 모듈을 실행합니다. **Go 1.27.1을 선택한 macOS arm64**가 필요합니다. 원본 JWT 소스를 로컬 `jwt-source`에서 사용하므로 모듈·모델 다운로드가 필요 없습니다.

```sh
cd experiments/short-claim/next-cohort-jwt-audit/cost-preview
GOTOOLCHAIN=local GOWORK=off GOPROXY=off GOSUMDB=off GOTELEMETRY=off \
  CGO_ENABLED=0 GOMAXPROCS=1 GOMEMLIMIT=64MiB \
  go run . < ../OBSERVER-INPUT.actual.public.v1.json
```

이 명령은 컴파일과 **새 API 실행**입니다. 저장된 증거 재생과 구분해야 하며, 첫 실행의 별도 캡처 도구가 제공한 제한·CPU/RSS 기록을 자동으로 재현하지 않습니다. [PROTOCOL](PROTOCOL.md)과 소스의 `author-only` 문구는 실행 전에 고정한 준비 상태를 보존한 것입니다. 실제 실행 여부와 수치는 [실행 기록](EXECUTION.actual.public.v1.json)과 [첫 응답](OBSERVATIONS.actual.public.v1.json.gz)을 기준으로 읽습니다. 이 문서는 이 비용 패킷의 CI 통과나 외부 게시 완료를 주장하지 않습니다.

## 출처와 라이선스

원본은 [golang-jwt/jwt의 고정 커밋](https://github.com/golang-jwt/jwt/tree/73c870b18e68b6e654b2b03f485aa3c9fab32cea)이며, 복사한 25개 파일과 [MIT 전문·원 저작권 고지](jwt-source/LICENSE)를 유지했습니다. 자체 코드·설명·가상 입력은 Apache-2.0입니다. [소스 지문](SOURCE-PINS.public.v1.json)과 [고정 Go SDK 관련 고지](../TOOLCHAIN-NOTICES.v1.json)를 함께 제공합니다. 전체 SDK 본문을 배포하거나 전체 계보·모델 학습 권리를 인증한 것은 아닙니다.

공개 키와 토큰은 가상 시험 자료이며 실제 사용자 인증정보를 포함하지 않습니다. 공개 첫 stdout은 125,979바이트를 바꾸지 않고 gzip으로 보관했습니다. 사적 호스트 경로가 있는 전체 프로세스 기록은 비공개로 보관하고, 공개 실행 기록에서는 그 범위를 설명합니다.

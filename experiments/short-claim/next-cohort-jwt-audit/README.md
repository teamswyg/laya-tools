# JWT 원본 판정과 다음 비용 비교

라우터가 도움이 되는지를 판단하려면 먼저 실제 프로그램의 정답과 비용을 알아야 합니다. 가상의 세션 토큰 13개를 준비하고, 요청 4개에 각각 입력 5개와 후보 정책 8개를 적용했습니다. 원본 JWT 라이브러리의 `ParseWithClaims`를 **실제로 160회** 호출했으며 첫 결과·실패 상태·자원 사용량을 보관했습니다. 모델 실행과 새 학습은 0회입니다.

## 무엇을 확인했나

| 가상 요청 | 원하는 정책 | 다섯 입력의 기대 수락 | 실제로 다섯 입력을 모두 만족한 후보 |
| --- | --- | --- | --- |
| Lantern | alpha 또는 beta를 대상으로 한 세션 | T T T F F | WithAudience |
| Harbor | alpha와 beta를 모두 대상으로 한 세션 | F F T F F | WithAllAudiences |
| Moss | 만료 시각을 반드시 포함 | F T F F T | WithExpirationRequired |
| Cove | 시간 검사에 2초 여유 | T F T F T | WithLeeway |

T는 해당 입력을 수락한다는 뜻입니다. 후보가 요청을 만족한다는 T와는 구분합니다. 관측된 토큰 수락은 100회, 거절은 60회입니다. 요청·후보 조합 32개에서는 **일치 4개·불일치 28개·미확인 0개**였습니다. 서명 검사·디코딩·입력 불변성 확인이 완료된 결과만 비교했습니다. 원래 기대값은 바꾸지 않았습니다.

이것은 다섯 입력에 대한 유한 일치입니다. 시간·발급자·주체의 모든 경계, 모든 JWT 구현, 실무 요청의 정답을 증명하지 않습니다. 공개 코드를 이미 읽고 만든 예제이므로 전체 JWT 계보를 `development_validation`으로 묶습니다. 독립 평가 자료 또는 2,400개 작업을 확보한 것으로 세지 않으며, 학습 자료에 바로 넣지 않습니다. 준비 입력의 기존 null 역할을 수정하지 않고, 결과를 보기 전에 별도의 [역할·대조군 동결 기록](FAMILY-CONTROLS.freeze.v1.json)을 채택했습니다.

## 메모리와 시간은 어떤가

Apple M4 Pro, Go 1.27.1, `GOMAXPROCS=1`의 첫 실행입니다. Go 코드의 병렬 실행 슬롯은 1개이며 실제 OS 스레드 수를 1개로 제한한 것은 아닙니다. 원본 판정 프로세스의 OS 최대 RSS는 **12,517,376B ≈ 11.94MiB**, 전체 자식 CPU 시간은 **23.689ms**였습니다. `main`에서 입력 검사와 160회 판정, 결과 구성을 포함한 시간은 **9.607ms**이고, 프로세스 시작부터 입출력 정리까지는 **598.010ms**였습니다. 프로세스 시작 비용이 이번 작은 작업에서 크게 보입니다. 이 차이는 측정 범위가 다른 관측이며 순수 시작 시간의 분리 측정은 아닙니다.

RSS는 Go 힙이나 모델 메모리가 아닙니다. 이 시험은 Go CPU 실행이며 Laya 추론·GPU 사용·에이전트 토큰 절감을 측정하지 않았습니다. `GOMEMLIMIT=64MiB`는 부드러운 Go 메모리 목표이고 256MiB RSS 기준은 실행 뒤 검사입니다. 강제 RSS 제한으로 설명하지 않습니다. 키가 살아 있는 동안 프로파일이나 덤프를 만들지 않았습니다.

## 왜 바로 모델을 학습하지 않나

후보 순서를 잘 정하면 검사 횟수는 줄어들 수 있습니다. 그러나 토큰의 서명 확인과 파싱을 같은 요청 안에서 안전하게 재사용하면, 남는 일은 저렴한 정책 검사일 수 있습니다. 작은 모델도 그보다 비싸다면 도움이 되지 않습니다.

다음 비교는 고정 순서, 요청 문구에서 미리 정한 수동 순서, 단순 검색을 대조군으로 둡니다. 서명·디코딩을 매번 하는 방식과, 같은 토큰·키·알고리즘·디코더·소스에서 검증된 claims만 재사용하는 방식을 분리합니다. 캐시에는 최종 `Token.Valid`나 정책 결과를 넣지 않습니다. audience와 시간 객체를 복사하고 매 후보의 정책을 다시 검증합니다. 캐시 조회·복사·정렬·처음 준비하는 비용도 포함해 실제 실행에서 비교해야 합니다. 이번 160개의 시간을 더한 가상 절감량을 실제 가속으로 주장하지 않습니다.

## 저장된 결과를 직접 확인하기

저장된 첫 API 응답과 원래 기대값을 Go로 비교할 수 있습니다. 이 명령은 원본 API·모델·학습을 실행하지 않습니다.

```sh
go run ./experiments/short-claim/next-cohort-jwt-audit/replay
```

`observer`는 별도 Go 모듈입니다. `testdata/jwt-source`의 원본 25개 파일을 그대로 사용하며 네트워크나 모델 다운로드가 필요 없습니다. 이 재실행은 새 원본 판정이고 저장된 결과 읽기와 구분해야 합니다. `runner`는 Mac arm64에서 첫 자식 응답과 CPU/RSS를 기록하는 별도 모듈입니다. 두 모듈의 테스트는 경계·오류 처리용이며 실제 OS 동작 전체를 대신하지 않습니다.

## 출처와 라이선스

원본은 [golang-jwt/jwt 고정 커밋](https://github.com/golang-jwt/jwt/tree/73c870b18e68b6e654b2b03f485aa3c9fab32cea)입니다. 복사한 원본에는 [MIT 전문과 원 저작권 고지](observer/testdata/jwt-source/LICENSE)를 보존했습니다. 자체 관찰 코드·가상 입력·설명은 Apache-2.0입니다. Go SDK는 설치된 고정 SDK의 지문과 관련 고지를 검토했고 전체 SDK 본문을 보관하거나 배포했다고 주장하지 않습니다. 모델의 학습·배포 권리는 이 코드 검토와 별도로 확인해야 합니다.

공개 키와 토큰은 이 시험에서 생성한 가상 자료입니다. 실제 사용자 토큰·사적 코드·인증정보·모델 본체를 포함하지 않습니다. 첫 비공개 기록에는 환경 경로가 있으므로 공개하지 않으며, 공개 API 응답은 바이트를 바꾸지 않고 별도로 복사했습니다. 테스트 준비 도구의 실패와 원본 실행은 [실행 기록](EXECUTION.actual.public.v1.json)에서 구분합니다.

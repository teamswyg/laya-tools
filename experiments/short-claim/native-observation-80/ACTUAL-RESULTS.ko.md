# 공개 함수 동작 검증과 학습 자료 확장

UUID Parse·Scan과 기존 Ordinal 함수의 **24개 유한 입력이 실행 전에 고정한 기대값과 모두 일치했습니다.** 한 번 실행했고 재시도하지 않았습니다. 작은 주장 모델에 줄 근거를 만드는 단계이며, 모델 정확도·라우팅 성능·Codex 비용 절감은 이번에 측정하지 않았습니다.

작은 힌트 모델은 비싼 검사 전에 후보의 확인 순서를 제안하려는 도구입니다. 학습하려면 어떤 주장이 공개 코드의 실제 동작과 맞는지 먼저 알아야 합니다. 이번에는 오류 후 남는 값, nil 여부와 객체가 바뀌는 시점을 확인했습니다. 설명에서 이런 조건을 생략하면 학습 정답도 틀릴 수 있습니다.

[사전 Want](want-authorship/WANTS.v1.json)는 그대로 유지하고 [실제 값](native/RESULT.v1.json)은 따로 기록했습니다. 잘못된 `ge` 바이트를 가진 32자리 UUID는 부분 결과가 `…fe00`, 하이픈이 있는 36자리 형식은 `…0000`으로 남았습니다. “오류면 배열은 전부 0”으로 합치면 잘못입니다. Scan의 nil interface·typed nil bytes·빈 bytes도 입력에서 구분했습니다. 네 nil/empty 사례는 기존 receiver를 유지했습니다. 이 결과를 모든 UUID 입력이나 Scan 사용에 일반화하지 않습니다.

실행 전에 원문·관찰기 파일 33개의 핀을 확인하고 외부 기록을 예약했습니다. UUID 초기화는 main보다 먼저 실행되므로 실제 초기화·내부 재귀 호출 수는 계측하지 않았습니다. 원문에서 읽은 초기화 위치 4개를 실제 호출 4회라고 보고하지 않고 실측은 null입니다. stdout·최종 파일·마지막 partial snapshot은 모두 67,635바이트로 SHA까지 같습니다. [사후 검사](saved-author-qa/RECEIPT.v1.json)는 Want 작성자의 비맹검 기록 무결성 검사이며 독립 정답 승인이나 인간 blind 검증이 아닙니다.

전체 프로그램 최대 RSS는 **18,104,320바이트, 17.265625 MiB**였습니다. 반올림한 wall time은 1.21초, user CPU 0.02초, system CPU 0.07초이며 controller는 별도로 1.217474375초를 측정했습니다. 초기화·해시 검사·JSON·반복 checkpoint 저장까지 포함하므로 개별 함수나 모델 추론 비용이 아닙니다. Go heap·GPU 메모리는 측정하지 않았고 Laya·GPU 추론도 실행하지 않았습니다. Go soft heap 256 MiB는 설정이며 RSS hard cap이나 실측값이 아닙니다. RAM 절감 비교도 하지 않았습니다. [측정 범위](native/OS-METRICS.v1.json)를 보존합니다.

24개 입력은 **독립 요청 24개 또는 2,400개 평가 달성**을 뜻하지 않습니다. 검증된 행동 범위에 맞는 요청과 후보 주장을 만들고 양성·음성의 차이를 확인한 뒤, 연관 원천과 차용 코드가 학습·평가 양쪽에 섞이지 않게 역할을 배정해야 합니다. 이 변환은 아직 수행하지 않았습니다. 기존 세 요청 비교에서는 단순 기준선이 이미 이상적인 확인 수에 도달했으므로 같은 세 요청만 재학습할 개선 여지가 없습니다.

이 계획은 이미 실패 결과가 공개된 FP32 모델 두 개를 그대로 두고, 입력 캡션에 필요한 행동 조건을 적으면 후보 확인 순서가 달라지는지 살펴보는 개발 진단이다. 학습, 파인튜닝, Laya·LLM·MPS 호출은 하지 않는다. 아직 점수 계산도 하지 않았다. 정답·역할·가중치·그룹은 여전히 미배정 상태다.

datasize, querystring, shlex의 같은 3개 논리 부모와 부모당 3개 후보를 사용한다. 요청75 v4의 영어 요청은 각각 27·32·21 단어이고, 모든 입력은 기존 512 B·32 정규화 단어 한도를 그대로 따른다. 한국어 설명은 표시용이며 별도 데이터나 언어 성능 실험이 아니다. A는 기존 공개 원문 캡션, B는 별도 버전의 소스 기반 행동 캡션이다. 요청·실제 코드·후보 순서·코드 정답은 A/B에서 동일하게 유지하고 캡션만 바꾼다. code-SAT 3P6N은 현재 제안이며, 최종 독립 검토 후 별도의 typed truth로 고정되어야 실행할 수 있다. 제안을 이 계획에서 실제 라벨로 바꾸지 않는다.

모델 입력은 영어 request와 해당 후보의 caption뿐이다. 소스·도움 함수·ID·라이선스·정답·Want/Got·마스크·역할은 입력 특징에 넣지 않는다. 현재 전체 후보에 대해 같은 코드 정답을 평가한다는 의미이지, A의 짧은 캡션에 모든 정답 조건이 있다는 의미는 아니다. A의 정보 부족은 진단할 원인으로 보존한다. 새 캡션이 모델 학습 당시와 다른 표현이라는 점도 결과 해석에 포함한다.

71의 BCE 모델과72의 BCE+RankNet λ1 모델은 각각 32,792 B의 고정된 `RIIDOH01` FP32 파일이다. HF의 정확한 revision과 SHA는 PLAN JSON에 고정했다. 모델 파일은 준비 중에 내용 확인·Decode하지 않았고, 기존 original/readback 네 파일의 존재·regular-file·크기만 확인했다. 32 KB급 파일이 총 RAM을 뜻하지 않는다. 기존 Go Decode는 모델 하나당 65,536 B의 FP64 계수를 만들며 특징과 기타 배열은 별도다. 새 생성 모델이나 새 계수가 생기는 실험이 아니다.

예정된 단일 실행은 `2 models × 2 arms × 9 candidates = 36` Features 호출과36 Score 호출이다. 중복된 모델별 특징 계산까지 명시적으로 세고 자동 재시도하지 않는다. 입력 준비는6개 parent-arm, Decode는2개 모델, 기존 Baselines는6개 parent-arm에 적용하며 각 호출이 네 비교 방식을 반환한다. 내부 정규화 호출을 개별 계측하지 않으면 별도 정확한 호출 수를 주장하지 않는다. 실행·controller·binary는 후속 작업이고, 이번 준비에서 실행한 것은 JSON/소스 참조 확인뿐이다.

기존72 saved driver의 네 방식 `fixed_order → bm25 → lexical_ordered → narrow_rule`을 재사용한다. 점수 동률은 원래 후보 순서를 유지한다. 기존 구현의 BM25 상수와 lexical 단어/인접 두 단어의 가중치를 바꾸지 않는다. 이번 요청은 일반 영어이므로 narrow_rule은 기존 `unsupported_rule_request`의 BM25 fallback을 기록해야 한다. 새로운 비교 도구를 만들지 않는다. 예전 검증에서 가장 좋았던 lexical_ordered를 고정 참고점으로 유지한다. 네 결과를 모두 공개하고, arm별 최소 checks 비교자를 설명한다면 동률은 위 배열 순서를 사용하며 이를 새 모델 선택이나 arm 선택에 이용하지 않는다.

주 결과는 각 고정 모델의 부모별 A/B 순서와 checks 차이다. checks는 첫 정답까지의 위치이며, 정답이 없는 경우 전체 후보 수다. unknown은 실패로 라벨링하지 않고 감사 분모에 남긴다. 전체 checks와 mean checks(부모 수로 나눈 값), Top1/answerable, Top3/answerable을 같은 분모로 기록한다. 이번에는 부모당 후보3개이므로 정답이 있는3부모의 Top3는 항상3/3이다. Top3만 좋아졌다고 주장할 수 없으며 실질적인 순서 구분은 checks와 Top1에 있다. 실제 verifier나 LLM 비용을 재지 않으므로 checks를 비용 절감으로 바꾸어 말하지 않는다.

9개 평가 후보를 모두 보존한다. A의 loss 적격 제안4N0P와 B의3P6N은 향후 학습 마스크 정보이며 고정 모델 평가 분모를 지우는 근거가 아니다. 현재72는 endpoint SampleWeights 곱을 사용해0 endpoint의 pair gradient/NLL 기여도0으로 만들고, 해당 행과 pair를 감사에 보존한다. 보존과 학습 기여는 다르다. A/B 공통 학습 적격 교집합에는 양성 pair가0개라 이3부모만으로 학습 가능한 paired A/B 실험을 주장할 수 없다. 이번 고정 모델 진단은 그 학습 실험과 별개다.

실행 자원 제안은 CPU1, Go soft heap256 MiB, 부모별 기존12 KiB JSON 한도, 전체 입력·결과 각각1 MiB, 외부60초 timeout 후 프로세스 회수다. 모델 읽기는 각각 정확한32,792 B와 고정 SHA를 검증한 뒤 Decode한다. 전체 프로세스 wall/CPU/RSS와 Go heap·누적 allocation을 구분한다. soft heap은 OS RSS의 하드 제한이 아니다. 불완전 결과·에러·초과 한도를 남기고 후보 삭제·가짜0 점수·자동 재시도로 성공을 만들지 않는다. 과거5% utility 기준은 변경하지 않지만 이번 작은 진단에서 그 기준을 새 합격 판정으로 적용하거나 production을 활성화하지 않는다.

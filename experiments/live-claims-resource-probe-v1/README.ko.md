# 작은 주장 모델의 반복 호출 비용

[English](README.md) · [측정값 전체](measurements.json) · [실제로 측정한 Go 코드](replay/main.go)

텍스트가 바뀔 때마다 작은 모델을 여러 번 호출하는 용도에 실행 비용이
충분히 작은지 확인했습니다. **기존 공개 Go 연구 모델**에 새로 작성한
라벨 없는 문장 8개를 반복 입력했고, 프로그램 안에서 직접 호출하는 방식과
같은 모델의 로컬 웹 API를 호출하는 방식을 각각 세 회차 측정했습니다.

이 결과는 개발용 자원 측정입니다. 모델의 정확도·일반화·운영 보장이나
뤼이도에서 큰 LLM의 사용량을 줄였다는 증거는 아닙니다.

직접 호출은 `Predict`를 실행한 구간을 잽니다. 루프 처리량에는 시간 측정,
체크섬 계산, 반복 결과 확인도 들어갑니다. HTTP 시간에는 요청 작성·로컬
통신·서버 계산·응답 읽기·JSON 해석·모델 지문 확인이 들어갑니다. 두 값의
차이를 순수 네트워크 비용으로 계산하거나 다른 모델의 속도 개선이라고
해석하면 안 됩니다.

직접 호출 30,000회마다 전체 측정 구간에서 **16바이트·할당 1회**가 관측됐습니다.
관측 할당량은 매우 작지만 `Predict` 함수만의 할당이 정확히 0회라는 뜻은
아닙니다. HTTP 클라이언트의 회당 할당 중앙값은 8,622.347바이트, 약 8.420KiB입니다.

서버가 따로 반환한 `inference_us`의 회차별 평균 중앙값은 4.510µs
(4.505–4.935µs)였습니다. 정수 마이크로초라 양자화가 있고 클라이언트와 측정
구간도 다릅니다. 이 값을 클라이언트 시간에서 빼서 통신 비용을 추정하지 않습니다.

## 메모리와 CPU 수치의 범위

`/usr/bin/time -l`의 최고 RSS는 **각 측정 프로세스 전체**입니다. HTTP 열은
클라이언트만 포함하고, 이미 실행 중이던 서버의 메모리·CPU는 제외합니다.
이 클라이언트는 비교 지문을 확인하려고 모델을 중복 로드했으며 GC 후 힙
차이가 81,208바이트였습니다. 따라서 HTTP 열을 실제 최저 메모리 클라이언트나
모델 자체의 크기로 해석하지 않습니다.

Go 힙 수치에는 시간 표본과 측정용 자료 구조도 있습니다. 직접 호출은
30,000개짜리 `int64` 배열 두 개, 원소 합계 480,000바이트를 유지하고, HTTP는
600개짜리 두 배열, 원소 합계 9,600바이트를 유지합니다. 모델·작업 공간의
스택 배치와 코드·런타임 페이지도 RSS에 영향을 줍니다. Go 메모리 수치는
네이티브·GPU 메모리 수치가 아닙니다. 이번 경로는 `CGO_ENABLED=0`인 순수 Go
CPU 추론으로 GPU가 필요하지 않았습니다.

별도로 실행 중인 데모 서버를 한 번 확인했을 때 RSS는 12,064KiB
= 12,353,536바이트 = 11.78125MiB, 프로세스 경과 시간은 약 16분50초,
표시 CPU는 0.0%였습니다. 정확한 UTC 시각은 기록하지 않았습니다.
**순간값이며 최고 사용량이나 이번 여섯 회차와 시점을 맞춘 측정이 아닙니다.**
주 결과 표에는 합치지 않았습니다.

외부 CPU·벽시계 시간은 0.01초 단위로 반올림되며 시작·모델 지문 확인과
로드·준비 호출·명시적 GC·출력까지 포함합니다. HTTP에서는 서버 CPU가
포함되지 않습니다. 첫 직접 호출 프로세스의 외부 경과 시간은 0.75초,
측정 루프는 0.141440초였고, 이후 외부 경과 시간은 0.14초·0.12초였습니다.
컴퓨터 전체 CPU 사용률이나 장시간 부하 결과는 측정하지 않았습니다.

## 고정한 실험 조건

- Apple M4 Pro, 물리·논리 CPU 14개, RAM 24GiB, macOS 26.6.2 (25G83),
  darwin/arm64에서 측정했습니다. 다른 작업이 동시에 실행됐을 수 있습니다.
- Go 1.27.1, `CGO_ENABLED=0`, `GOWORK=off`, `GOTOOLCHAIN=local`,
  `GOPROXY=off`, `GOMAXPROCS=2`, `GOMEMLIMIT=128MiB`입니다.
  `GOMEMLIMIT`은 Go 런타임의 소프트 한도이고 프로세스 전체의 강제 한도가 아닙니다.
- 모델 파일은 73,988바이트, 기록된 학습 단계 4,240,
  SHA-256 `cfd35ee70a23f94a8d470b7dea596244a91ac7f1410475e8a42959693c99864b`입니다.
  기존 HF semanticcontrast parent21이며 모든 프로세스에서 **로드 전에 지문을
  확인**했습니다. 모델·시드·매개변수를 선택하거나 새 학습을 하지 않았습니다.
- 작업자 1개, 직접 호출 작업 공간 1개를 재사용했습니다. 각 방식마다 새
  프로세스 세 개를 `직접1→HTTP1→직접2→HTTP2→직접3→HTTP3` 순서로 실행했습니다.
- 직접 방식은 회차당 준비 128회·측정 30,000회로, 합계 **90,384회**입니다.
  HTTP는 준비 32회·측정 600회씩 **POST 1,896회**, 앞뒤 상태 확인 GET 6회를
  더해 **HTTP 요청 1,902회**입니다. 준비 호출은 시간 표에서 제외했습니다.
- 기존 `127.0.0.1:8877` 서버를 사용했고 새로 시작하거나 재시작하지 않았습니다.
  상태 확인 여섯 번 모두 모델 지문·단계·연구 모드·미검증 상태·작업자 1개와
  기존 신뢰도 0.9·점수 차이 0.05·온도 1을 확인했습니다.
- 각 방식의 내부 작업 한도는 55초였습니다. 실제 측정 루프는
  0.042–0.141초로 짧으며 지속 부하 실험은 없습니다.
- 새 원본 문장 8개, 영어 5개·한국어 3개를 라벨 없이 고정 순환했습니다.
  UTF-8 길이는 **52, 54, 50, 51, 51, 64, 63, 71바이트**, 평균 57바이트이고
  JSON 본문은 **63, 65, 61, 62, 62, 75, 74, 82바이트**입니다.
  길이를 포함해 묶은 입력 지문은
  `0a81f50a71ff1e8e7a988188034cb1989bbe0f41fec92fe21350ed8cbfa2b3b1`입니다.
- 첫 여덟 판정의 체크섬은 모든 회차에서 `ac8b22815a94d3b3`으로 같습니다.
  전체 측정 루프는 직접 `8e2766d9b9cfd615`, HTTP `6d7cb4a547b59523`으로
  회차 간 같습니다. 전체 호출 수가 달라 두 방식의 전체 체크섬은 다릅니다.
  모든 반복 입력의 결과를 첫 결과와 비교했고, 수치·판정 필드를 체크섬에
  넣었습니다. 결과가 사용되지 않는 벤치마크를 막고 재현성을 확인하는
  장치이지 의미 정답을 확인하는 장치는 아닙니다.
- 측정 전 저장소 HEAD는 `798edb6157fe3723a11f18f54718b58e156b6ddb`입니다.
  관련 코드·측정 코드·바이너리·원본 기록의 지문은 [전체 JSON](measurements.json)에 있습니다.

이 문장들은 공개된 개발용 입력입니다. 최종 2,400개 자료나 모델·선택기
튜닝에는 넣지 않습니다. 보호된 연구 자료 조회, 실제 앱 쓰기, 새 학습,
표시 기준 변경, 모델 배포 또는 원시 프로파일 수집은 없습니다.

## 직접 재현하기

측정 때 사용한 [Go 코드](replay/main.go)를 바이트 그대로 공개했습니다.
그 안의 8개 문장은 이번 자원 실험을 위해 만든 원본이며 비공개 업무 내용이
없습니다. 원본 코드 지문과 같고, 단위 표기 오류를 수정하거나 측정을
다시 돌리지 않았습니다. 모델 파일·로컬 원시 로그는 Git에 넣지 않습니다.

저장소 루트에서 [웹 데모 안내](../../docs/live-claims-demo.ko.md)에 따라
고정 모델을 `.cache/live-claims-demo/model/claims.rsc`에 받고, HTTP 방식에는
기존 데모 서버를 실행합니다. Go 1.27.1로 빌드합니다.

```sh
CGO_ENABLED=0 GOWORK=off GOTOOLCHAIN=local GOPROXY=off \
  go build -trimpath -ldflags='-s -w' -o bin/claim-resource-probe \
  ./experiments/live-claims-resource-probe-v1/replay
```

`GOMAXPROCS=2 GOMEMLIMIT=128MiB`를 사용해 여섯 회차를 앞서 적은 고정 순서로
각각 새 프로세스에서 실행합니다. macOS의 첫 두 회차 예시는 아래와 같습니다.

```sh
GOMAXPROCS=2 GOMEMLIMIT=128MiB /usr/bin/time -l \
  ./bin/claim-resource-probe -arm inprocess -repeat 1
GOMAXPROCS=2 GOMEMLIMIT=128MiB /usr/bin/time -l \
  ./bin/claim-resource-probe -arm http -repeat 1
```

호스트 부하에 따라 시간이 달라집니다. 분위수를 합치거나 서버 시간을 빼서
통신 비용이라고 주장하지 않고, 시점이 맞지 않는 프로세스 최고 RSS도 더하지
않습니다. 이 코드는 유지보수용 실험이며 앱 실행 의존성이 아닙니다.

## 보존한 단위 표기 문제

측정 코드가 서버의 정수 마이크로초 분포에도 나노초 분포 구조체를 재사용했습니다.
원본 JSON의 `server_inference_reported_us` 안에는 `mean_ns`, `p50_ns` 등의
필드 이름이 있지만 **그 숫자의 단위는 마이크로초**입니다. 공개 집계는 이를
`mean_us`, `p50_us` 등으로 명시하고 숫자는 바꾸지 않았습니다. 원본 기록과
측정 코드·바이너리를 보존했고, 오류를 감추기 위한 재측정은 하지 않았습니다.

# 작은 모델이 문장에서 보존하는 정보 점검

[English](README.md) · [원본 입력·측정값](results.json) · [측정한 Go 코드](replay/main.go)

학습 전에 모델의 특징 추출 코드가 문장의 어떤 정보를 담고 어떤 정보를
줄이는지 확인했습니다. 새로 만든 라벨 없는 문장 쌍 12개, 총 24개만 사용했고
모델을 로드하거나 판정·학습하지 않았습니다. 이 입력들은 공개된 개발용
진단 자료로, 최종 2,400개 자료나 선택기 튜닝에 넣지 않습니다.

## 실제로 확인한 것

- 24개 중 23개를 처리했습니다. 유효한 UTF-8이지만 4,097바이트인 한 입력은
  거부했습니다. 4,096바이트 안에서는 전체 문장을 읽으며 별도 토큰·문장·단서
  개수 제한이나 중간 잘라내기는 없습니다.
- 영어와 한국어의 물음표·부정·인용·시제 표현을 바꾼 일곱 쌍은 특징이
  달라졌습니다. 단서를 일부 담는다는 증거이며 정확한 의미 인식이나 일반화의
  증거는 아닙니다.
- 절을 인용·직접 보고 위치 사이에서 바꾼 세 쌍은 2,048개 특징 값의
  float32 비트와 단어 수가 같았습니다. 전체 문장 순서를 그대로 저장하는
  표현이 아니라는 증거입니다. 이 교환이 세 주장 항목에서 실제 의미 정답을
  바꾸는지 독립적으로 확인하지 않았으므로 판정 오류라고 주장하지 않습니다.
- 그 세 쌍은 희소 특징을 순회하는 순서가 달랐습니다. 부동소수점 합산 순서가
  결과에 영향을 줄 수 있어 실제 모델 점수·판정까지 비트가 같다는 뜻은 아닙니다.
- 정확히 4,096바이트인 합성 입력의 2,048개 단어를 모두 셌으며 끝의 마침표를
  물음표로 바꾸면 특징 8개가 달라졌습니다.

## 문장이 숫자로 바뀌는 방식

계약 이름은 `utf8-word12-char2345-fnv1a-signed-logtf-l2-2048-v2`입니다.
[특징 추출 코드](../../pkg/statehintwide/features.go#L122)는 최대 4,096 UTF-8
바이트의 전체 입력을 읽고 각 Unicode 글자를 소문자로 바꿉니다. 단어는
Unicode 문자·숫자의 연속이고, 모든 단어와 인접 단어 쌍을 사용합니다.
구두점은 앞 단어 기록을 초기화하지 않습니다.

공백·구두점을 포함한 소문자 글자열의 모든 2–5글자 조각도 사용합니다.
여기서 글자는 바이트가 아니라 Unicode rune입니다. 위치·전체 순서·더 긴
명시적 조각은 별도로 보관하지 않습니다. 모든 조각을 부호 있는 FNV-1a
해시로 2,048칸에 모으고, 부호가 있는 빈도를 합쳐 `log1p`와 L2 정규화를
적용합니다. 반대 부호가 같은 칸에 모이면 0으로 상쇄될 수 있습니다.

한국어 활용은 띄어쓰기 단어와 짧은 글자 조각으로 남습니다. 형태소 분석·
어간 추출·Unicode 정규화는 없고, 질문·부정·인용을 따로 해석하는 파서나
화자·시제·구문 범위 필드도 없습니다. 실제 판정 모델은 이 숫자 특징을
사용하며 원본 사건 사실·태스크 상태·참조 라벨을 특징에 넣지 않습니다.
[입력 뷰](../../pkg/statehintwide/contextual_api.go#L13)는 작업 공간을 빌려
보여주므로 측정 코드는 재사용 전에 수치를 복사했습니다.

## 추출 결과

변경된 칸 수는 정규화된 float32 비트를 비교한 값입니다. 한 부분을 바꿔도
전체 L2 정규화 때문에 여러 칸이 바뀔 수 있으므로 언어 단서 개수가 아닙니다.
아래 L2 차이는 반올림했고 JSON에는 원래 정밀도를 보존했습니다.

| 쌍 | 새 라벨 없는 입력의 차이 | 단어 수 A/B | 바뀐 칸 | L2 차이 |
|---|---|---:|---:|---:|
| p01 | 영어 끝 `.` / `?` | 6/6 | 114 | 0.253461 |
| p02 | 영어 `not` 삽입 | 6/7 | 148 | 0.474338 |
| p03 | 영어 따옴표 추가 | 6/6 | 112 | 0.249712 |
| p04 | 영어 현재 / 미래 표현 | 6/6 | 150 | 0.836990 |
| p05 | 한국어 `닦았습니다.` / `닦았습니까?` | 3/3 | 60 | 0.614283 |
| p06 | 한국어 `접었습니다.` / `접지 않았습니다.` | 3/4 | 80 | 0.888244 |
| p07 | 한국어 `다듬고 있습니다.` / `다듬을 예정입니다.` | 4/4 | 100 | 0.937158 |
| p08 | 영어 두 절의 인용 / 직접 보고 위치 교환 | 17/17 | 0 | 0 |
| p09 | 영어 두 절의 채택 / 부정된 채택 위치 교환 | 28/28 | 0 | 0 |
| p10 | 한국어 두 절의 인용 / 직접 보고 위치 교환 | 16/16 | 0 | 0 |
| p11 | 4,096바이트 합성 입력 끝 `.` / `?` | 2,048/2,048 | 8 | 0.081180 |
| p12 | 유효 한국어 UTF-8 4,096 / 4,097바이트 | 372/거부 | — | — |

p01의 첫 입력은 활성 칸 112개 중 110개만 0이 아니었습니다. 두 칸의 부호
합계가 완전히 상쇄됐지만 특정 언어 단서가 사라졌다고 판정한 것은 아닙니다.
세 순서 교환은 첫·끝 네 글자와 첫·끝 단어가 같은 절을 교환해 지역 조각
집합을 유지했습니다. 실제 정답 구분이 필요하다는 독립 증거 없이 이것만으로
특징 계약 변경이 필요하다고 결론 내리지 않습니다.

그 세 쌍의 조밀 특징 지문은 각각 다음과 같습니다.

- p08: `cda7a7d237f11bd7184a9a8fce62f9101b213ee3eca73f34a82b9ae2cf9ca551`
- p09: `52e2751f83f73c55587f3e279af465feca31bbc600ce35aa79678d186b702fef`
- p10: `f01283910a6ba0277ec95a04229a3e67e343912f051450bd264d15d5ab3a7a23`

p11은 `q `를 2,047번 붙이고 `q.` 또는 `q?`로 끝냈습니다. p12는
`청록색 고리를 차례로 닦습니다. `를 93번 붙이고 공백 세 개와 마침표로
4,096바이트·1,678 rune을 만든 뒤 `!`를 하나 추가한 쌍입니다. 거부된 쪽의
JSON 숫자 0은 비어 있는 자리 표시자이며 실제 추출 측정값이 아닙니다.

4,096바이트에서 가능한 최대 단어 수는 2,048개입니다. 한 바이트 단어
2,048개와 한 바이트 구분자 2,047개가 최소 4,095바이트이고, 2,049개는
최소 4,097바이트가 필요합니다. 한국어의 사용 가능 글자 수가 더 작은 것은
Hangul rune의 UTF-8 바이트 수 때문이며 별도 한국어 단어 제한이 아닙니다.

## 다음 실험에서의 의미

현재 예정된 두 형제 모델의 데이터 비교는 특징 계약을 그대로 유지합니다.
지역 단서와 한국어 활용형의 데이터 범위는 살펴볼 학습 가설입니다.
지역 조각 밖의 인용·범위 관계, 해시 상쇄·정규화의 정보 감소는 별도 표현
가설로 남깁니다. 이번 12쌍으로 새 표현을 선택하거나 모델 오류·개선·운영
정확도를 주장하지 않습니다.

## 재현

저장소 루트에서 Go 1.27.1로 실행합니다.

```sh
GOWORK=off GOTOOLCHAIN=local GOPROXY=off GOMAXPROCS=2 GOMEMLIMIT=128MiB \
  go run ./experiments/claim-feature-information-audit-v1/replay
```

코드에 포함된 새 원본 입력의 특징 추출만 실행합니다. 모델·데이터셋을
로드하지 않으며 계약을 바꾸지 않습니다. 같은 소스 계약에서는 기록된
수치를 재현해야 합니다. 공개를 위해 새 입력이나 모델 판정을 만들지 않았습니다.

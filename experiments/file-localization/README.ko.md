# 실제 파일 위치 평가 — 실험 34, 실행 준비

[평가 계획](plan-34.json)을 결과 확인 전에 고정했다. 이 문서는 실행 계약이며 아직 실제 작업의 검색 순위를 평가하지 않았다.

같은 2,400개 요청 원문과 수정 전 전체 파일 경로를 사용한다. 원래 파일명 BM25, 기존 `NormalizeText`로 식별자를 나눠 읽는 BM25, 두 순위의 baseline-first 병합을 모두 보고한다. 주 비교는 원래 검색과 병합이다. 학습·임계값 조정·좋은 결과만 선택하는 과정은 없다.

`fileeval.Rank`는 요청과 파일 경로만 받는다. 정답은 순위가 완성된 뒤 `Measure`에만 전달한다. 변환된 검색 텍스트가 같아도 서로 다른 파일은 별도 후보로 유지한다. 보조 입력이 한도를 넘으면 기존 순위로 돌아가고 fallback 횟수를 보고한다.

전체 2,400개를 분모로 Hit@1/10/100과 MRR을 계산하며 저장소별 결과도 제공한다. 기존 파일 정답이 없는 새 파일 전용 2개를 삭제하지 않는다. 전체 정답 경로 수·후보에서 찾은 경로 수·모든 정답이 첫 10개에 들어오는지도 별도로 집계한다. 최소 한 개 정답이 후보에 있는 작업에서만 첫 정답까지 20개 단위 페이지 수와 개선/악화/동일 작업 수를 비교한다. 이 비용 비교의 적용 작업 수를 명시한다.

주 비교의 사전 기준은 적용 작업의 총 페이지 수가 늘지 않고 전체 Hit@10이 낮아지지 않는 것이다. 통과하더라도 파일 위치 lexical 기준선의 결과일 뿐, 작업 해결·난이도·분할·실제 LLM 비용 절감이나 제품 준비 완료가 아니다. 페이지 계산은 정답을 정확히 알아보는 동일 비용 확인을 가정한다. 수정 파일은 관련 파일의 완전한 정답 목록도 아니다.

```sh
go run ./cmd/riido-fileeval --out .cache/file-eval-new
```

고정된 요청·정답 projection과 2,400개 전체 로컬 파일 목록 캐시가 필요하다. 네트워크를 사용하지 않으며 하나라도 미확보면 첫 순위 계산 전에 오류로 종료한다. 실제 불완전 캐시에서 이 방어 동작을 확인했다. 일부 확보된 작은 저장소만 평가해 최종 결과처럼 기록하지 않는다. 최종 채점은 수집 완료 후 수행한다.

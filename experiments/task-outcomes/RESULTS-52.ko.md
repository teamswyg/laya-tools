# PDCA 52: 실제 비교 실행과 2,400개 확보 준비

[English](RESULTS-52.en.md) · [봉인한 계획](plan-52.json) · [전체 수치](results-52.json) · [2,400개 확보 계획](../../docs/golden-set-acquisition.ko.md)

서로 다른 공개 개발 작업 **3개**를 요청 프로필 `gpt-6-sol / low`, `gpt-6-luna / low`로 각각 수행했다. 고정한 **6개 CLI 시도를 모두 기록**했다. 독립 검사에서는 6개 후보의 선언된 변경 범위를 모두 수용했으나, **실행 종료와 사용량까지 확인된 시도는 5개**다. 나머지 하나는 120초 제한에 걸렸고 사용량은 미확인이다.

이는 한 저장소·두 코드 가족의 작은 개발 비교다. 두 요청은 정확한 주석 변경이다. 실제 라우팅의 최종 2,400개 평가나 대표적인 모델 능력·비용 절감을 증명하지 않는다. 이전 요청을 다시 수행해도 고유 요청 수를 새로 늘리지 않는다.

## Act

두 주석 요청에서는 같은 작업의 수용과 사용량 비교가 가능해졌다. Luna의 관측 시간이 더 짧고 토큰도 적었지만 두 작은 사례의 기술적 관찰이다. 워크로드 절감·구독 효율 또는 더 큰 모델이 항상 필요 없다는 근거가 아니다. 기능 요청의 Sol6 사용량이 없어 세 요청의 전체 비용 비교도 완성되지 않았다.

Laya의 기존 세 CPU 사전 예측은 임계값 0.9에서 모두 보류한 기록으로 보존한다. 기존 standard의 6.1 Sol 매핑을 이번 6 Sol의 새 예측으로 해석하지 않았고, 새 Laya 실행·학습·임계값 변경·운영 등록도 하지 않았다. 이전 cold 전체 프로세스 최대 RSS 약 1.48GB는 초소형 메모리 목표를 충족한 값이 아니다.

확대 준비로 **별도 versioned 행동 계약**을 추가한다. 첫 대상 `repo-keyword-language-guard`는 선택된 저장소 후보의 키워드까지 기존 문자 보호를 적용하는 작업이다. 원본 revision·파일·LICENSE/NOTICE·명세·독립 검사·필수 package/test 종료를 묶는다. 변경 없는 기준, 독립 정답 후보와 알려진 오류 후보로 수락기를 점검한다. **이 새 행동 요청의 실제 모델 결과는 아직 없다.** 이번 6회는 이를 사용하지 않은 기존 실행기로 수행했다.

게시 전 독립 검토에서 중간 키워드나 세 번째 이후 후보를 생략하는 두 잘못된 구현의 수용을 발견했다. 새 계약을 후보 수 1~8의 모든 선택 위치와 32개 키워드 위치, 네 문자 종류에 대해 강화하고 두 오류 구현을 회귀 검사에 추가했다. 내부 4,608개 키워드 검사는 **한 요청의 수락기를 검사하는 assertion**이며, 골든셋 4,608개를 새로 확보했다는 뜻이 아니다. 기존 봉인한 세 요청의 명세는 바꾸지 않았다.

[확보 계획](../../docs/golden-set-acquisition.ko.md)은 개발 12~24→120→240 이상, 별도 학습·선택·보정, 영역별 최종 2,400 이상을 구분한다. Go final의 서로 다른 여섯 작업 종류, 30개 이상 저장소·한 저장소 비중 10% 이하 수집 목표, 연결 그룹·저장소 분리, 두 프로필 비교 최소 4,800 CLI 시도와 미확정 비용 처리도 명시한다. 숫자는 앞으로의 목표이며 확보·실행 결과가 아니다. 검색 protected final 2,402개는 계속 미평가다. 새 가중치 배포나 운영 라우팅 활성화는 하지 않았다.

## CI에서 발견한 실행기 정리 문제

첫 [PR73 CI](https://github.com/teamswyg/laya-tools/actions/runs/36795753610)는 Linux·비밀 검사에 통과했지만 macOS의 하위 프로세스 종료 검사에서 실패했다. 해당 테스트에서는 정리를 확인하지 못한 후보를 스냅샷하거나 수용하지 않았다. 실제 6개 모델 시도의 원본 종료 기록과 구별되는 실행기 테스트 실패다.

로컬 반복 검사에서는 수정 전 20회 중 2회 실패했다. 독립 재현에서는 종료했지만 아직 회수하지 않은 좀비만 남은 프로세스 그룹에 신호를 보낼 때 `EPERM`, 회수한 뒤에는 `ESRCH`를 관측했다. 이는 [Apple XNU의 그룹 신호 처리](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sig.c)와 일치한다. **CI 로그 자체가 당시 errno를 입증한 것은 아니다.**

수정은 기존 2초 제한 안에서 일시적인 `EPERM`을 다시 확인한다. `ESRCH`로 그룹 부재를 관측해야만 정리가 완료되며, 계속 `EPERM`이거나 살아 있으면 `cleanup_unknown`을 유지한다. 제한·수용 조건을 낮추지 않았다. 오류 시퀀스 검사와 실제 종료 반복 검사, 독립 검토를 통과했으며 수정한 commit의 CI가 별도 병합 조건이다.
